# Step catalog — every Step kind, delivered and pending

A **Pipeline** is a chain of **Steps**: `collect → parse → transform steps… → sink`. Two vocabularies
describe the chain, and this page is the one place both are laid out side by side:

1. **Step kinds** — the authorable node types the engine executes today (`BuiltinNodeType`, served
   with their attribute specs by `GET /pipelines/node-types`; the specs are pinned by
   `node-attributes.contract.json`). Each has a recipe **verb** (what `RecipeCompiler` and the
   `steps[]` chain call it) and a **node type** (what the graph, the flat file and the palette call
   it). Part A documents every one. ⚠ The separate recipe-verb catalogue `GET /pipelines/step-types`
   and its `step-types.contract.json` were retired 2026-09-24 (`STEP-TYPES-DEAD-CLIENT-MIRRORS-1`): the Recipe view was
   their last reader, and the verb vocabulary's one owner is `RecipeCompiler`'s verb switch.
2. **Step Processors** — the 119<!--count:processors-->-entry product taxonomy the palette lists in eight families
   (`processor-catalog.contract.json`, `ProcessorCatalog.java`, served as
   `GET /pipelines/processor-catalog`). A processor is a *label* over a Step kind or an engine
   capability, never a Java class of its own ([catalog-vs-executors](../engine/catalog-vs-executors.md)).
   Part B lists all of them by status: **51**<!--count:processors-delivered--> delivered, **17**<!--count:processors-partial--> partial
   (something ships, not as a chain Step, or not the whole promise), **51**<!--count:processors-planned--> **planned**
   (the palette shows them inactive — *"Not yet available"*). The board rendering of the same list is
   [`EDITIONS.md` § Step Processors](../../../EDITIONS.md); both come from one contract, regenerated by
   `ProcessorCatalogContractTest` with `-Dprocessor.catalog.write=true`, never hand-edited.

## The two lanes (read this before authoring a chain)

| Lane | Steps that execute there | How it runs | Example runner |
|---|---|---|---|
| **Ingest** | `collect`, every `parse` frontend, `route`, `sink` | The poll cycle: files land as Consignments, parse + map + sink in one pass. `route:` forks the write into one destination per branch. | `run-example …` (one shot) |
| **At rest** | `filter`, `dedup`, `join`, `summarize`, `sql` — the `steps[n]:` chain | Stage-1 lands the store; a `type: pipeline` Job (`pipeline_config: <the same file>`, `on_pipeline: <id>`) lifts the chain (`PipelineLift.stageTwo`) and runs it over the landed store on every commit, writing the top-level `output_store:`. A chain with no `output_store:` refuses to lift; an active pipeline whose chain no Job runs is an orphan finding. | `serve-example … --demo` |

Two grammars spell the same chain: the **flat file** (`steps[n]:` list of single-key maps, or the
legacy singular `processing.dedup:` / `processing.join:` / `processing.summarize:` / `csv_settings.where` /
`route:` blocks — mutually exclusive with `steps[]`, projected in the order `filter → join → dedup →
summarize → route`) and the **recipe** (`RecipeCompiler`), which compiles to the flat form. Route
branches may chain their own `steps[]`, limited to `filter` (with `where:`), `dedup` (consignment scope)
and `summarize` — `RouteArming.BRANCH_STEP_KINDS`; a `join` or a nested `route` refuses at save and at
registration. Mechanism detail: [execution-lanes](execution-lanes.md), [live-execution](live-execution.md),
[editable-round-trip](editable-round-trip.md).

**Every delivered Step kind has a runnable example** in two places: standalone under
[`inspecto/examples/`](../../../../inspecto/examples/README.md) (`07-steps/` + `02-parsing/`) and, wired
together in one space, `spaces/default/config/<kind>_step/` (+ `asn1_example`, `xml_example`, and the
format-example pack), seeded by `spaces/default/data/samples/seed-inbox.{sh,ps1}`.

# Part A — the delivered Step kinds

Configuration tables are the served `AttributeSpec`s (key · type · tier · default · help), the same
contract the editor renders. **Flat-file spelling:** a key shown as `a.b` is nested (`a: { b: … }`) in
the `*_pipeline.toon`; a `list` is `key[n]: v1, v2`. Tier is the editor's disclosure bucket
(required · optional · advanced), not validation.

## `collect` → `acquisition` — the Collector

**Function.** The pipeline entry: discovers the files (or the Dataset snapshots) one run will take,
lands them in the inbox, and decides what counts as *new*. Exactly one per pipeline (`collector()` is
singular by construction).

**Behaviour.** Each acquire cycle lists the source through the Connection's connector (`local` inbox,
SFTP/FTPS, JDBC export, Azure Blob, Kafka, or `dataset` to consume another pipeline's parquet
snapshots), applies the include/exclude patterns, the stability window, the file-grain duplicate
policy (`path` marker · `metadata` · `checksum` · `etag`) and the post-success action, then packs the
admitted files into Consignments (`consignment.max_files` / `max_bytes`, ordered by arrival `mtime` or
`name`). Compressed inputs are unpacked here with fail-closed caps. Gap detection over a numbered series
(`gap_detection.sequence: ORDERS_{yyyyMMdd}`) raises `SEQUENCE_GAP`. The trigger keys give the pipeline
its own cadence or make it fire on a Dataset write.

**Flat-file home.** The `collector:` block plus `dirs.poll`, `processing.file_pattern`,
`processing.duplicate_check` / `marker_extension` / `retention_days`, `processing.unpack`, and the
top-level `trigger:`. The UI flattens the nested keys with `__`, shown here as dots.

**Refusals.** `connector: dataset` without `dataset:` (and the reverse) refuse at load. A Connection
that is not `local` needs a saved Connection profile.

**Configuration — the `collector:` block** (2026-09-23, `PROCESSOR-RELEASE-READINESS-1` G5). Unlike the
other Part A tables this one is the **parser's** key set (`PipelineConfigParser.parseCollector` + the
consignment caps), not only the served `AttributeSpec`s, because the canvas form is a curated subset.
*Form* names the acquisition-node attribute (`__` = nesting; `NodeAttributes.COLLECTOR`); *spec* marks a
leaf `ConfigSpecs.pipeline()` declares, so `POST /config/write` and the graph save type-check it. Every
sub-block is additive: absent means the default in the table. *Remote* = read only on the remote
acquisition path (`CollectorProcessor.acquire`); a `local` inbox never reaches it, and since 2026-09-24 a save
warns when one is set on a local inbox (`WARN_COLLECTOR_KEY_INERT`, [config safety](../config/config-safety.md#collector-checks--throttle-breaker-archive-2026-09-24)).

## `parse` → the **7**<!--count:parser-node-types--> `parser.*` frontends

**Function.** Turns a landed file into typed rows named by the schema's `raw.fields[]`
(`selector` = position, header name, JSON key, capture group or dotted record path, depending on the
frontend). The schema also carries the **mapping** — the Record Transformer that shapes those rows —
so `parse` and `map` are one node in the graph. Structural mismatches are rejected to `errors/`
(or the file is quarantined), never silently dropped; type-cast failures become NULL through `TRY_CAST`.

**Configuration.** The `parsing:` block: `frontend:` picks the family, and one sub-block carries that
family's grammar. A `parsing.grammar: grammar/<id>` reference (or a path) reuses a saved Grammar
component; inline keys win. `processing.schema_file` names the schema; `processing.csv_settings.date_formats`
/ `timestamp_formats` are required for any DATE / TIMESTAMP column, whatever the frontend.
The served step-type contract carries no per-frontend attributes: the parse surface is schema-driven
by the served grammar (`parsing-attributes.ts` in the UI). The keys each frontend reads:

| Frontend (node type) | `parsing.` block and its keys | Selector means | Example |
|---|---|---|---|
| `parser.delimited` | `delimited: {delimiter, quote, comment, has_header, skip_header_lines, skip_junk_lines, skip_tail_lines, null_strings[], date_formats[], timestamp_formats[], strict_mode, engine}` | column position (`"0"`) or header name | `01-ingest/hello-csv`, `02-parsing/pipe-delimited`, `02-parsing/no-header`, `csv_example` |
| `parser.fixedwidth` | `fixedwidth: {record: line\|bytes, trim, min_record_length, fields[n]{name,start,length}}` | field name from the slice table | `02-parsing/fixedwidth`, `fixedwidth_example` |
| `parser.json` | `json: {format: auto\|newline\|array, records_path, maximum_object_size}` | JSON key (dotted path) | `02-parsing/json-frontend`, `json_example` |
| `parser.text_regex` | `text_regex: {pattern}` — named capture groups; a non-matching line is dropped | group name | `02-parsing/text-regex-frontend` |
| `parser.xlsx` | `xlsx: {sheet, range, header, normalize_names, ignore_errors, stop_at_empty}` — DuckDB `read_xlsx`, needs the `excel` extension (`ExcelExtension`, cached or `-Dduckdb.extension.dir`), loaded fail-closed | normalised header cell | `02-parsing/xlsx-frontend`, `excel_example` |
| `parser.asn1` | `asn1: {grammar (inline X.680 text), root_type, strictness: BER\|DER\|CER, file_header_length, record_header_length, max_value_bytes, segments: {recordType: schemaPath}}` — sugar for the plugin wiring below with `Asn1RecordIngester` | dotted path into the decoded record (`party.number`); `EVENT_TYPE` is derived | `02-parsing/asn1-frontend`, `asn1_example` |
| `parser.plugin` | `plugin: {ingester: <FQCN of a StreamingFileIngester>, segments: {recordName: schemaPath}, ingester_config: {…plugin keys}}` (legacy spelling `processing.ingester` / `segments` / `ingester_config`). Shipped ingesters: `XmlRecordIngester` (`record_element`, `namespace_aware`, `encoding`), `FixedWidthRecordIngester` (`record_length`), `Asn1RecordIngester`. | one schema per **segment** (record kind); undeclared kinds are counted as junk | `02-parsing/xml-plugin-frontend`, `xml_example` |

**Refusals.** An unknown `frontend` is refused with the list. `frontend: asn1` beside an explicit
`plugin:` block refuses (two bindings). A plugin ingester with no `segments` refuses. A schema type
outside the engine's DuckDB scalar list refuses at load. A parser is always format-specific: the
generic `parser` type is authoring-legacy, retyped to `parser.<frontend>` on Apply.

**Behaviour worth knowing.** `has_header` skips the header; `skip_header_lines` is *added on top* for
junk preamble. Plugin-ingester pipelines have **no single schema**: the planner labels their
consignments `schema` (a `null` there threw until 2026-09-06). A segment's output lands under
`database/<segmentKey>/`.

## `transform` → `transform.filter` — Row filter

**Function.** Keep or drop rows. Two shapes: a **post-map SQL predicate** (`where:`, over the typed,
mapped columns — the one an explicit `steps[]` filter runs), and the **pre-parse text filters**
(`include_regex` / `exclude_regex` / `include_prefixes` / `exclude_prefixes` against one raw column,
`filter_target_column`) that speak raw-column vocabulary.

**Behaviour.** `RowShaper.filter` splits the input into `data` (kept) and `dropped` — a counted reject
relation, so nothing disappears unaccounted. ✅ **The INGEST lane keeps it too, since 2026-09-22 (`WB-09`/`D2`)** — a parse-rejected row is counted in
the batch ledger's `rejected_rows`, and `total_input_rows` includes it, so nothing disappears
unaccounted on either lane. 🔴 It did not until then: the ledger reported `rejected_count=0` for a file
that lost a truncated record, with input and output both excluding it, so the counters reconciled while
the record was missing. See [`consignment-status-flow.md`](../engine/consignment-status-flow.md). A NULL predicate result drops the row. Mid-branch (inside
`route:`) a filter must carry `where:`; a blank predicate or a pre-parse key refuses to arm. At rest the
legacy pre-map filter (`csv_settings.where`) is refused because the landed store no longer has raw columns.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `where` | string | required | — | **Row predicate (after parsing).** SQL over the mapped, typed columns. Rows matching are kept; NULL results are dropped. |
| `include_regex` | list | optional | — | **Include matching (before parsing).** Keep rows whose target column matches any of these regexes, checked on the raw text before parsing. |
| `exclude_regex` | list | optional | — | **Exclude matching (before parsing).** Drop rows whose target column matches any of these regexes. |
| `include_prefixes` | list | optional | — | **Include by prefix (before parsing).** Keep rows whose target column starts with any of these. |
| `exclude_prefixes` | list | optional | — | **Exclude by prefix (before parsing).** Drop rows whose target column starts with any of these. |
| `filter_target_column` | number | advanced | — | **Target column index.** Which raw column (0-based) the four before-parsing lists above match against. Ignored by the row predicate. |

**Example.** `examples/07-steps/filter` (8 → 4 rows) · `spaces/default/config/filter_step`.

## `lookup` → `transform.lookup` — Lookup & static map transcoder

**Function.** Transcode one column's values through an inline static map — `NEW → Open`, `SHIPPED → Done`
— without a reference store. The first PARTIAL Step Processor delivered (2026-09-06); a *versioned* lookup
that changes over time is still `transform.join` over a `produces: reference` pipeline.

**Behaviour.** `RowShaper.lookup` compiles the map to a `CASE CAST(column AS VARCHAR) WHEN 'k' THEN 'v' …
END` — keys and values are author **literals**, quoted through `sqlStr`, never SQL and never guarded as SQL.
In place (`SELECT * REPLACE`) unless `target` names a new column; an unmatched value passes through unchanged
unless `default` sets the literal it becomes. Comparison is textual, so a numeric code column maps without a
cast. Emits `data` only — a lookup changes values, never row counts. No legacy singular spelling: a chain
holding one always takes the `steps:` form (like `sql`); the recipe verb is `lookup`, config verbatim.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `column` | string | required | — | **Column to transcode.** The typed, mapped column whose values are looked up. |
| `mappings` | list | required | — | **Mappings (key=value).** One entry per code: the value found, `=`, the value to write. The one spelling — a map-valued attribute type is refused on purpose. |
| `target` | string | optional | in place | **Write to column.** A new column for the result; blank replaces the source column. |
| `default` | string | optional | pass through | **Unmatched values become.** The literal written when no mapping matches. |

**Example.** `examples/07-steps/lookup` (8 rows, `STATUS_LABEL` = Open/Done/Void) · `spaces/default/config/lookup_step`.

## `explode` → `transform.explode` — Array exploder

*Added 2026-10-06 (operator, 2026-10-06: build `transform.explode` as a NEW type; `transform.split` stays
the grandfathered, non-authorable ancestor and is not un-grandfathered).*

**Function.** One output row per element of an array column — a CDR's charge items, an order's lines —
so a nested feed becomes a flat fact table without hand-written SQL.

**Design (decisions, operator, 2026-10-06).**
- **What explodes.** A DuckDB `LIST` column (any element type, `LIST<STRUCT>` included) is unnested as is.
  A `VARCHAR` / `JSON` column holding a **JSON array** is cast to `JSON[]` first, so each element lands as
  a `JSON` value a following `sql` step can pick apart (`elem->>'amount'`). This is the shape every
  `parser.json` feed produces: the parser lands each key as VARCHAR. A JSON value that is not an array
  (an object, a scalar, malformed text) is treated like `null` — an empty array — never as an error,
  because one odd record must not fail the batch. Any other column type (a bare `STRUCT`, a number) is
  **refused at run, naming the type**: a struct is one value, there is nothing to explode.
- **Empty / null arrays.** `on_empty: keep` (default) keeps the row once with a `null` element and a `null`
  index; `on_empty: drop` drops it. Dropping is opt-in because a vanished parent row is silent data loss.
- **Order and index.** Elements come out in array order; `index_column` (optional) adds the element's
  **1-based** position. Compiled as `UNNEST(list_transform(arr, (x, i) -> {e: x, i: i}))`, not a `LATERAL`
  join, because a lateral join does not keep element order.
- **Identifiers.** `column` must be a column of the inbound relation (checked at run against `DESCRIBE`, and
  at save against the declared schema when it is known). New names (`as`, `index_column`) must match
  `[A-Za-z_][A-Za-z0-9_]{0,127}` and must not collide with a kept column or each other. Every name is
  quoted through `SqlIdent.q`; nothing the author types is spliced into SQL unquoted.
- **The array column itself.** Dropped by default (`keep_source: false`), so `as` defaults to the source column's
  own name; `keep_source: true` keeps it beside the element and then needs a distinct `as`.
- **Lane.** A `steps:` kind with no legacy singular spelling (like `lookup`), so it executes **at rest**
  with `output_store:`. It is not admitted mid-branch (`RouteArming.BRANCH_STEP_KINDS` unchanged). It
  amplifies rows, so `ConservationCheck` leaves it out, as it does `transform.split`.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `column` | string | required | — | **Array column.** A LIST column, or a VARCHAR/JSON column holding a JSON array. |
| `as` | string | optional | the source column's name | **Element column.** The column each element is written to. |
| `index_column` | string | optional | none | **Index column.** Adds the element's 1-based position. |

## `unpivot` → `transform.matrix.unpivot` — Unpivot / column flattener

*Added 2026-10-06 (operator, 2026-10-06).*

**Function.** Wide columns become `(name, value)` rows — a per-hour `H00 … H23` usage row, a quarterly
`Q1 … Q4` sheet — so a matrix-shaped feed can be grouped and charted like any long table.

**Design (decisions, operator, 2026-10-06).**
- **Name.** The node type keeps the catalog id `transform.matrix.unpivot`; its `steps:` kind is the plain
  word `unpivot` (a dotted TOON key would read as a path). Because the type is not `transform.<kind>`, the
  lift maps a kind to its type through `BuiltinNodeType.typeForStepKind`, not by string concatenation;
  `BuiltinNodeTypeFlatHomeTest` pins that every `STEP` case round-trips through it.
- **Which columns.** Exactly one of `columns` (a list of inbound names) or `columns_pattern` (a Java
  regular expression, matched with *find* — the same partial-match rule as DuckDB's `COLUMNS('…')` — against
  each inbound name, in declaration order). The pattern is resolved in Java against `DESCRIBE`, so only
  real, quoted column names reach SQL. A listed column that does not exist, a pattern that matches nothing,
  or both keys at once is refused. Every other column passes through unchanged and is repeated per row.
- **Type coercion (stated rule).** Every unpivoted column is `CAST` to `value_type` **before** the unpivot,
  so the value column has exactly one declared type whatever the input mix. Default `VARCHAR` — every DuckDB
  type converts to text, so the default never fails. Allowed: `VARCHAR`, `BOOLEAN`, `INTEGER`, `BIGINT`,
  `DOUBLE`, `DATE`, `TIMESTAMP`, `DECIMAL(p,s)`. The cast is strict (`CAST`, not `TRY_CAST`): a value that
  does not convert **fails the run** rather than landing as a silent `null`.
- **Nulls.** A `null` cell produces no row by default (DuckDB's `UNPIVOT`); `include_nulls: true` keeps it.
- **Identifiers.** `name_column` (default `name`) and `value_column` (default `value`) must match
  `[A-Za-z_][A-Za-z0-9_]{0,127}`, differ from each other and from every passed-through column.
- **Lane.** Like `explode`: a `steps:`-only kind, executed at rest, not admitted mid-branch, and left out of
  `ConservationCheck` (it multiplies rows).

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `columns` | list | optional | — | **Columns to unpivot.** Inbound column names. Exactly one of this or `columns_pattern`. |
| `columns_pattern` | string | optional | — | **Column name pattern.** A regular expression; every inbound column it matches is unpivoted. |
| `name_column` | string | optional | `name` | **Name column.** Receives the unpivoted column's name. |
| `value_column` | string | optional | `value` | **Value column.** Receives the cell value. |
| `value_type` | select | optional | `VARCHAR` | **Value type.** Every unpivoted column is cast to it first. |
| `include_nulls` | boolean | optional | `false` | **Keep empty cells.** Emit a row for a `null` cell too. |

**Example.** `examples/07-steps/unpivot` — a nested JSON CDR feed whose per-call charge breakdown arrives as
wide `charge_*` keys, unpivoted into `(CHARGE_TYPE, AMOUNT)` rows.

## `resample` → `transform.timeseries.resample` — Time-grain resampler & gap imputer

*Added 2026-10-17 (ANALYTICS-CORE-1 M5, [analytics-kernel § Time-series primitives](../analytics-kernel.md#time-series-primitives)).*

**Function.** One row per key per time bucket, **every bucket between the bounds present** — a daily, weekly or
monthly series ready for a chart, a KPI or a shift, with no missing periods.

**Behaviour.** The SQL is the Analytics Kernel's (`TimeSeriesSql.resample`), bucketing by its one truncation
definition (`TimeGrain`): `second` · `minute` · `hour` · `day` · `week` (Monday, ISO) · `month` · `quarter` · `year`.
- **Measures** speak the one measure grammar (`count` | `agg(field)`, the same aggregates as `summarize`, evaluated by
  `MeasureCompiler`); output columns are the measure ids (`count`, `sum_AMOUNT`).
- **Gap fill** (as Anomaly D-AD8): a bucket with no rows gets **0** for `count`, `countDistinct` and `sum`, and
  **empty** for every other aggregate (an average of nothing is not 0).
- **Series.** Every key seen in the data gets the whole series, from `from` (or the earliest bucket with data) to `to`
  (or the latest), both truncated to the grain. A key's empty value is a key of its own; a row whose time is empty is
  left out. A series of **100,000 buckets or more** fails the run (narrow `from`/`to` or use a coarser grain).
- **The clock is always stated.** A `DATE` or zone-less `TIMESTAMP` column is bucketed on its own clock and takes no
  `timezone`. A `TIMESTAMP WITH TIME ZONE` column **needs** `timezone` (a region id such as `Europe/Berlin`, or `UTC`)
  and is bucketed on that zone's wall clock — never DuckDB's session zone, which is the host's. The bucket column is
  then that zone's local start time (a `TIMESTAMP`). Both mismatches are refused at run and at save.
- Identifiers are validated (`[A-Za-z_][A-Za-z0-9_]*`) and quoted; the output columns (keys, bucket, measure ids) must
  differ. Runs **at rest** like every `steps:` kind; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `time_column` | string | required | — | **Time column.** The DATE or TIMESTAMP column the rows are bucketed on. Rows where it is empty are left out. |
| `grain` | select | required | — | **Time grain.** The bucket size. Weeks start on Monday. |
| `timezone` | string | optional | — | **Time zone.** Only for a TIMESTAMP WITH TIME ZONE column: whose calendar the buckets follow. |
| `group_by` | list | optional | — | **Series keys.** One series per key; every key gets every bucket. |
| `measures` | list | required | — | **Measures.** `count` or `agg(field)`; an empty bucket gets 0 for count, countDistinct and sum, empty otherwise. |
| `bucket_column` | string | optional | `bucket` | **Bucket column.** Receives each bucket's start. |
| `from` | string | optional | — | **First bucket.** `2026-01-01` or `2026-01-01T08:00`; blank = the earliest bucket with data. |
| `to` | string | optional | — | **Last bucket.** Blank = the latest bucket with data. |

**Example.** `examples/07-steps/timeseries` — 7 sales over 5 days in 2 regions → 10 day rows, empty days filled with 0.

## `shift` → `transform.timeseries.shift` — Period-over-period shift

*Added 2026-10-17 (ANALYTICS-CORE-1 M5).*

**Function.** Every row gains, per listed column, the value its key had **N buckets earlier** — the previous day,
the same month last year (`periods: 12` with `grain: month`), the next week (`periods: -1`).

**Behaviour.** `TimeSeriesSql.shift`: a self-join **by bucket**, not by row position — `time_column` truncated to
the grain, plus N grain-intervals, must equal the current row's bucket — so a series with a missing bucket gets an
empty value instead of the wrong period's. Every inbound row is kept, ordered by keys then time.
- The input must hold **one row per key per bucket** (a `resample`'s output). Two rows for one key and bucket are
  refused before the join (the earlier value would be ambiguous and rows would multiply).
- The added columns are `<column><suffix>` (default `_prev`); a name that collides with an inbound column is refused.
- `periods` is a non-zero whole number within ±10,000. The clock rule is resample's: `timezone` only, and always, for a
  `TIMESTAMP WITH TIME ZONE` column.
- Runs **at rest**; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `time_column` | string | required | — | **Time column.** The bucket column (a resample's output); one row per key per bucket. |
| `grain` | select | required | — | **Time grain.** The bucket size. Weeks start on Monday. |
| `timezone` | string | optional | — | **Time zone.** Only for a TIMESTAMP WITH TIME ZONE column. |
| `group_by` | list | optional | — | **Series keys.** Shift within each key. |
| `columns` | list | required | — | **Columns to shift.** Each gains a column with its value from the earlier bucket. |
| `periods` | number | optional | `1` | **Buckets back.** 1 = previous bucket; 12 with a month grain = same month last year; −1 = next bucket. |
| `suffix` | string | optional | `_prev` | **Name suffix.** `sum_amount` becomes `sum_amount_prev`. |

**Example.** `examples/07-steps/timeseries` — the resample's daily sums with the previous day's beside them.

## `forecast` → `transform.timeseries.forecast` — Time-series forecaster (Holt-Winters)

*Added 2026-10-17 (ANALYTICS-CORE-1 S5, [analytics-kernel § Forecasting](../analytics-kernel.md#forecasting)).*

**Function.** A forecast per key of a regular series — every bucket of the history with its one-step-ahead forecast
and prediction band, then `horizon` buckets ahead — so a chart, a KPI band or an Alert Rule reads actual, forecast,
lower and upper side by side.

**Behaviour.** The SQL is the Analytics Kernel's (`ForecastSql`, the DuckDB form of `Forecaster`).
- **Methods:** `holt_winters` (default; additive level, trend and season, weights `alpha` / `beta` / `gamma`, defaults
  0.25 / 0.02 / 0.15 — the `business-assurance` template's) or `seasonal_naive` (the same bucket one season earlier).
  Deterministic: nothing is fitted or searched.
- **Band:** a normal approximation, sigma = 1.4826 × MAD of the in-sample one-step errors, widened with the horizon;
  one row per bucket **per level** (`levels`, default 0.95).
- **Output columns:** the keys, `time_column`, `horizon` (0 = history, 1…H ahead), `actual` (empty ahead),
  `forecast`, `level`, `lower`, `upper` (all three empty on the first season). Ahead buckets are labelled last + h
  grains, in the time column's own type.
- **The input must be regular** — run a `resample` first. Refused before forecasting: a time value not on the grain,
  an empty time, a missing or repeated bucket, an empty value, a series shorter than two seasons, a time column that is
  not a `DATE` / zone-less `TIMESTAMP`, a value column that is not a number. Caps: `period` ≤ 1,000, `horizon` ≤ 1,000,
  10,000 buckets per series, 200,000 series (the run fails past them).
- Identifiers are validated and quoted; the keys and the time column may not take an output column's name. Runs **at
  rest**; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `time_column` | string | required | — | **Time column.** The DATE or TIMESTAMP bucket column of a regular series (a resample's output). |
| `grain` | select | required | — | **Time grain.** The bucket size. Weeks start on Monday. |
| `value_column` | string | required | — | **Value column.** The number forecast; an empty value is refused. |
| `group_by` | list | optional | — | **Series keys.** One forecast per key. |
| `method` | select | optional | `holt_winters` | **Method.** `holt_winters` or `seasonal_naive`. |
| `period` | number | required | — | **Season length.** Buckets per season (7 for a weekly pattern in daily data); every series needs two seasons. |
| `horizon` | number | required | — | **Buckets ahead.** |
| `levels` | list | optional | `0.95` | **Interval levels.** One lower/upper band (and row) per level. |
| `alpha` | number | advanced | `0.25` | **Level smoothing.** Holt-Winters only. |
| `beta` | number | advanced | `0.02` | **Trend smoothing.** Holt-Winters only. |
| `gamma` | number | advanced | `0.15` | **Season smoothing.** Holt-Winters only. |

**Example.** `examples/07-steps/forecast` — 28 days of sales resampled to days, then 7 days forecast with a 0.95 band.

## `similarity` → `transform.similarity` — Similarity score

*Added 2026-10-17 (ANALYTICS-CORE-1 S1, catalog `quality.match.fuzzy`, [analytics-kernel § Similarity kit](../analytics-kernel.md#similarity-kit)).*

**Function.** Every row gains a **0..1 score of how alike two of its text columns are** (a customer name and an
account name, a payee and a beneficiary) and, with a `threshold`, a **true/false candidate flag** for review.

**Behaviour.** The SQL is the Analytics Kernel's (`SimilaritySql`): DuckDB's built-in string functions, each with a JVM
twin the kernel's parity test holds equal bit for bit, so a score in the output can be recomputed outside DuckDB.
- **Methods.** `jaro_winkler` (default; `jaro_winkler_similarity`, prefix scale 0.1, prefix up to 4, boost above 0.7 —
  favours a shared beginning, good for names), `jaro`, `levenshtein` (`1 − edits / longer length`) and `token_jaccard`
  (shared words over all distinct words — word order does not matter).
- **Normalize first** (default on): accents stripped (canonical decomposition, marks removed), lower-cased, runs of
  spaces, tabs and line breaks collapsed to one space, ends trimmed — on both sides. No transliteration: `Müller` becomes
  `muller`, not `mueller`.
- ⚠ DuckDB's string functions count **UTF-8 bytes**: an accented letter left in place (normalize off) counts as two
  characters. Normalizing first removes the common case.
- A value that is empty (NULL) on either side gives an empty score and flag; a blank text scores 0. A non-text column is
  compared as its text.
- **Length cap — 1,000 characters per value** (`SimilarityStep.MAX_TEXT_LENGTH`, measured on the raw text before
  normalizing). Edit-distance and Jaro cost grow with the product of the two lengths, so a longer value **fails the run**
  with `transform.similarity: a value in '<left>' or '<right>' is longer than 1000 characters`, as the kernel's other caps
  fail closed. A NULL score was not used for it: NULL already means a side is empty, and would hide the refusal.
- ⛔ **A candidate, never an identity** (decision D-M1). The flag says a pair is worth a look. The Step never merges,
  links, drops or reorders rows, and nothing may read the flag as "the same entity".
- Identifiers are validated (`[A-Za-z_][A-Za-z0-9_]*`) and quoted; the added columns must not collide with an inbound
  column. Runs **at rest** like every `steps:` kind; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `left` | string | required | — | **Left column.** The first text of each pair. |
| `right` | string | required | — | **Right column.** The second text of each pair, from the same row. |
| `method` | select | optional | `jaro_winkler` | **Method.** `jaro_winkler` · `jaro` · `levenshtein` · `token_jaccard`. |
| `normalize` | boolean | optional | `true` | **Normalize first.** Strip accents, lower-case and collapse spaces on both sides before scoring. |
| `score_column` | string | optional | `similarity` | **Score column.** Receives the score, 0..1. |
| `threshold` | number | advanced | — | **Candidate threshold.** 0..1; when set, adds the candidate flag: score ≥ threshold. |
| `candidate_column` | string | advanced | `similarity_candidate` | **Candidate column.** Receives the flag; only with a threshold. |
| `keep_score` | boolean | advanced | `true` | **Keep the score.** Off keeps only the flag (needs a threshold). |

Refused at save, at compile and at run with the same words (`SimilarityStep.parse`): an unknown key, a missing or
non-identifier column, `left` = `right`, an unknown method, a threshold outside 0..1, `keep_score: false` with no
threshold, equal output names, and (against the declared schema) a column it lacks or an output that collides.

**Example.** `examples/07-steps/similarity` — 6 customer/account name pairs, Jaro-Winkler at 0.92: `José Müller` /
`Jose Muller` scores 1.0 (accents and case only); `Vladimir Putin` / `Putin, Vladimir` 0.43 (Jaro-Winkler reads order —

## `rank` → `transform.analytics.rank` — Rank & Top-N pruner

*Added 2026-10-17 (ANALYTICS-CORE-1 S4, [analytics-kernel § Ranking, sampling and pivot](../analytics-kernel.md#ranking-sampling-and-pivot)).*

**Function.** Ranks the rows of each group by a stated order — the top 3 calls per region, the largest invoice per
customer — and either **keeps the top N** or **adds the rank as a column**.

**Behaviour.** One DuckDB window function over the inbound rows (`RankStep`).
- **Methods.** `row_number` (default — 1, 2, 3: every row its own place), `rank` (1, 1, 3: ties share a place, a gap
  follows) and `dense_rank` (1, 1, 2: ties share, no gap).
- **The tie-break is mandatory and deterministic.** The window orders by `order_by`, then `tie_break`, each with its
  direction and **empty values last in both directions**. For `row_number` it then orders by **every remaining inbound
  column**, ascending, empty last — so two rows still tied are equal in every column, and either one gives the same
  output. The same input gives the same ranks in any arrival order. For `rank` / `dense_rank`, rows equal in `order_by`
  and `tie_break` share a rank by definition, so `top: N` keeps every row tied at place N (possibly more than N rows).
- `top` keeps rows ranked N or better in each group; `keep_rank: false` (needs `top`) drops the rank column.
- Identifiers are validated (`[A-Za-z_][A-Za-z0-9_]*`) and quoted; the rank column must not collide with an inbound
  column. Runs **at rest** like every `steps:` kind; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `order_by` | list | required | — | **Order by.** Columns that decide the rank, each `COL`, `COL asc` or `COL desc`. |
| `group_by` | list | optional | — | **Rank within.** The rank restarts per key. Blank: one ranking of all rows. |
| `method` | select | optional | `row_number` | **Method.** `row_number` · `rank` · `dense_rank`. |
| `top` | number | optional | — | **Keep top N.** 1 … 1,000,000; keep rows ranked N or better per group. |
| `rank_column` | string | optional | `rank` | **Rank column.** Receives the rank, from 1. |
| `tie_break` | list | advanced | — | **Tie-break.** Ordered after `order_by`, same spelling; must not repeat an `order_by` column. |
| `keep_rank` | boolean | advanced | `true` | **Keep the rank.** Off keeps only the top rows (needs `top`). |

Refused at save, at compile and at run with the same words (`RankStep.parse`): an unknown key, no `order_by`, an entry
that is not `COL [asc|desc]`, a column ordered twice, an unknown method, `top` outside 1 … 1,000,000, `keep_rank: false`
with no `top`, and (against the declared schema) a column it lacks or a rank column that collides.

**Example.** `examples/07-steps/rank` — 8 calls, the top 2 per region by amount: K02 and K03 tie at 40.00 and are

## `sample` → `transform.sample` — Statistical & reservoir sampler

*Added 2026-10-17 (ANALYTICS-CORE-1 S4, catalog `quality.sample.reservoir`, [analytics-kernel § Ranking, sampling and pivot](../analytics-kernel.md#ranking-sampling-and-pivot)).*

**Function.** Keeps a **fixed number** or a **share** of the rows of each group — a test extract of a large Dataset, an
audit sample per region — and keeps the **same rows on every run**.

**Behaviour.** The SQL is the Analytics Kernel's (`Sampler`), with a JVM twin its parity test holds equal.
- **The order.** Each row's key values become a key text (each value length-prefixed, an empty value marked), hashed
  with the seed as `md5_number_lower('<seed>:' || key text)` — the holdout split's MD5 reading. Within each group rows
  are ordered by that hash, then by the key text, then by every inbound column; the first rows are kept.
- **`size: k`** keeps `k` rows per group, or every row of a smaller group (reservoir semantics). **`fraction: f`** keeps
  `⌊(n · bp + 5000) / 10000⌋` rows of a group of `n` (`bp` = `f` in basis points): each group's own share, rounded to
  the nearest row, half up — a stratified sample.
- ⛔ **Never DuckDB's `USING SAMPLE` or `random()`** — neither is reproducible across runs, threads or versions, and
  neither has a JVM twin. The same input, key and seed give the same rows; another seed gives another sample. A row
  keeps its place as long as its key does, so added rows can only push a sampled row out, never reshuffle the rest.
- `key` defaults to every inbound column (two rows equal in every column are interchangeable). Columns pass through
  unchanged. Runs **at rest**; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `size` | number | optional | — | **Rows per group.** 1 … 1,000,000. Exactly one of this or `fraction`. |
| `fraction` | number | optional | — | **Fraction.** More than 0, at most 1, at least 0.0001 (one basis point). |
| `seed` | number | optional | `0` | **Seed.** Any whole number; the same seed picks the same rows. |
| `group_by` | list | optional | — | **Sample within.** Sample each key separately (stratified). Blank: one sample. |
| `key` | list | advanced | every column | **Row key.** The columns hashed with the seed. |

Refused at save, at compile and at run with the same words (`SampleStep.parse`): an unknown key, both or neither of
`size` / `fraction`, a size or fraction out of range, a seed that is not a whole number, and (against the declared
schema) a column it lacks; at run, an inbound column named with the sampler's reserved prefix `__sample_`.

**Example.** `examples/07-steps/sample` — 24 calls in three regions, `size: 3`, `seed: 42`, `key: [CALL_ID]`: 9 rows,
3 per region, the same 9 on every run (listed in its `probes.txt`, computed outside Java from the definition).

## `pivot` → `transform.matrix.pivot` — Pivot (rows to columns)

*Added 2026-10-17 (ANALYTICS-CORE-1 S4, [analytics-kernel § Ranking, sampling and pivot](../analytics-kernel.md#ranking-sampling-and-pivot)).*

**Function.** The reverse of `unpivot`: long rows become a wide table — one row per key, **one column per declared
value**, each holding one aggregate of that value's rows (usage per subscriber per call type, revenue per month column).

**Behaviour.** `PivotStep` writes `agg FILTER (WHERE CAST(pivot_column AS VARCHAR) = 'value')` per value, grouped by the
keys; the aggregate is the **Measure grammar's** (`MeasureCompiler.aggregateSql`: `count`, `countDistinct`, `sum`, `avg`,
`min`, `max`, `median`, `stddev`, `variance`, `p05` … `p99`) — no aggregate of its own.
- ⛔ **No dynamic pivot.** `values` is required and capped at **200**: a pivot over whatever values the data holds would
  make the output's columns depend on the data, which no schema, save check or later Step can judge.
- Values are matched **as text**. A row whose value is not listed, or is empty, adds to no column; its key still gets a
  row. A value with no rows gets 0 for `count` / `countDistinct`, empty otherwise.
- The column name is `prefix` + value and must be a plain column name (set `prefix` for a value such as `2024`); names
  must be distinct from each other and from the keys, ignoring case. `sum`, `avg` and the statistics need a numeric
  field (refused at run; at save a VARCHAR field fails open, as for every type check there).
- Runs **at rest**; not admitted mid-branch. The output's columns are the keys and the pivoted columns only.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `group_by` | list | optional | — | **Row keys.** One output row per key. Blank: one row. |
| `pivot_column` | string | required | — | **Pivot column.** Its values become columns; not also a key. |
| `values` | list | required | — | **Values.** 1 … 200 declared values, one column each. |
| `measure` | string | required | — | **Measure.** `count` or `agg(field)` in the Measure grammar. |
| `prefix` | string | optional | — | **Column prefix.** Put before each value to form its column name. |

Refused at save, at compile and at run with the same words (`PivotStep.parse`): an unknown key, no or too many
`values`, an empty value, a value that does not make a plain column name, duplicate names, a pivot column that is also a
key, a missing or unknown measure, and (against the declared schema) a column it lacks.

## `entity_link` → `transform.entity.link` — Entity grouping

*Added 2026-10-17 (ANALYTICS-CORE-1 S2, catalog `enrichment.entity.link`, [analytics-kernel § Entity grouping](../analytics-kernel.md#entity-grouping)).*

**Function.** Every row gains a **resolution group**: rows that agree exactly on a match key — the same email, the
same phone number — are the same entity, and the links chain (A shares an email with B, B a phone with C: one group).
The group id is the group's smallest key. Optionally, a **similarity review** flags look-alike rows of *other* groups
for a person to check.

**Behaviour.** The grouping is the Analytics Kernel's (`EntityGrouping`, run in DuckDB by `EntityGroupingSql`), whose
parity test holds the DuckDB result equal to a JVM union-find.
- **Match keys.** Each `match` entry is one way two rows are the same entity: one column, or several joined with `+`
  (`PHONE+LAST_NAME`: both must agree). Any entry is enough.
- **Normalising.** Before comparing, a column ignores accents, case and extra spaces (the similarity kit's
  normalisation); a column listed under `digits` keeps its digits only (`+44 20 7946-0001` = `442079460001`); one
  under `as_written` is compared as stored. A value that is **empty** — NULL, blank, or nothing left after
  normalising (`n/a` under `digits`) — **never matches**, so blanks cannot pull rows together.
- **Blocking.** With `blocking` columns, rows are compared only inside the same block (same value of every blocking
  column, normalised the same way). A row with an empty blocking value stays a group of its own.
- **Group id.** The key of the member whose key is smallest *as text* (`10` sorts before `9`), written in the key
  column's own type. It does not depend on row order.
- **Fails closed.** The run fails, naming the numbers and writing nothing, when the key is empty or repeated, when
  more rows than `max_block_size` share one match value or block (typically a placeholder such as `0` or `unknown`
  that would wrongly join them — filter it out first) or when the candidate pairs exceed `max_pairs`.
- ⛔ **Identity is never asserted by similarity** (decision D-M1). Match keys are exact. `candidate_by` scores a text
  column (the similarity kit: Jaro-Winkler by default) against the rows of **other** groups in the same block and
  adds `candidate_score`, `candidate_group` (the closest other group) and `candidate_review` (score ≥
  `candidate_threshold`). It never changes a group. A similarity knob offered as part of a match (`method`,
  `threshold`, `similarity`, `fuzzy`, `score`) is refused by name.
- Identifiers are validated (`[A-Za-z_][A-Za-z0-9_]*`) and quoted; the added columns must not collide with an inbound
  column. Runs **at rest** like every `steps:` kind; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `key` | string | required | — | **Record key.** A column that names each row once. A group's id is its smallest key (as text). |
| `match` | list | required | — | **Match keys.** One entry per way two rows are the same entity; join columns with `+`. |
| `blocking` | list | optional | — | **Blocking keys.** Rows are only compared inside the same block. |
| `digits` | list | optional | — | **Digits-only columns.** Compared on their digits only. |
| `as_written` | list | advanced | — | **Compare as written.** Compared exactly as stored. |
| `group_column` | string | optional | `resolution_group` | **Group column.** Receives the resolution group id. |
| `max_block_size` | number | advanced | `1000` | **Largest block.** 2..100,000; the run fails if more rows share one match value or block. |
| `max_pairs` | number | advanced | `1000000` | **Most candidate pairs.** 1..100,000,000. |
| `candidate_by` | string | advanced | — | **Review look-alikes by.** A text column scored against the other groups of the block; needs `blocking`. |
| `candidate_method` | select | advanced | `jaro_winkler` | **Review method.** `jaro_winkler` · `jaro` · `levenshtein` · `token_jaccard`. |

## `outlier` → `transform.stats.outlier` — Outlier detector & IQR boxplot fencer

*Added 2026-10-17 (ANALYTICS-CORE-1 S3, [analytics-kernel § Distribution Steps](../analytics-kernel.md#distribution-steps)).*

**Function.** Every row gains its group's outlier figures and a **true/false flag**: is this number unusual for its
own group (its region, its customer)?

**Behaviour.** The SQL is the Analytics Kernel's (`OutlierSql`), built on its `Stats` definitions.
- **`iqr`** (default) — Tukey's fences `Q1 − k·IQR` and `Q3 + k·IQR` (`k` 1.5; 3 = "far out"), the quartiles
  `quantile_cont` (`quantile_mode: continuous`, the kernel's default) or `quantile_disc` (`discrete`). Writes
  `<prefix>lower`, `<prefix>upper`, `<prefix>flag`; the flag is true when the value is **strictly** outside.
- **`robust_z`** — `(x − median) / max(1.4826 · MAD, max(unit, 5 % of |median|))`, the Anomaly Detection rule. Writes
  `<prefix>score`, `<prefix>flag`; the flag is true when `|score| > threshold` (default 3.5). `unit` (default 1) is the
  smallest change that matters — it keeps a near-constant group from flagging a tiny change.
- **Per group** — `group_by` columns; a NULL key is a group of its own; no `group_by` = the whole column.
- An **empty value** (NULL, or NaN in a floating column) gets no flag (and no score) but still sees its group's fences;
  a group with no value has no figures. A group of one value has fences equal to it: never flagged.
- The column must be a number (integer, DECIMAL, FLOAT, DOUBLE); refused otherwise. Every row is kept. A key of the
  other method (`k` with `robust_z`) is checked but has no effect. Runs **at rest**; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `column` | string | required | — | **Number column.** The number judged. |
| `method` | select | optional | `iqr` | **Method.** `iqr` · `robust_z`. |
| `group_by` | list | optional | — | **Groups.** Judge each value against its own group. |
| `k` | number | advanced | `1.5` | **Fence multiplier.** IQR only; 0–100. |
| `quantile_mode` | select | advanced | `continuous` | **Quartiles.** IQR only: `continuous` · `discrete`. |
| `threshold` | number | advanced | `3.5` | **Score threshold.** Robust z only; above 0. |
| `unit` | number | advanced | `1` | **Smallest meaningful change.** Robust z only; above 0. |
| `prefix` | string | advanced | `outlier_` | **Column prefix.** Names the added columns. |

Refused at save, at compile and at run with the same words (`DistributionStep.parseOutlier`): an unknown key, a
missing or non-identifier column, an unknown method or quantile mode, `k` outside 0–100, a threshold or unit not above
0, a prefix that does not make a plain column name, the column also grouped by, and (against the declared schema) a
column it lacks, an added column that collides, a text column.

**Example.** `examples/07-steps/outliers` — 14 payments in three regions: `P06` 960.00 is outside NORTH's fences
111.3125 … 157.8125, `P11` 15.00 outside SOUTH's 362.1875 … 435.6875; then binned (below).

## `binning` → `transform.data.binning` — Histogram & quantile binner

*Added 2026-10-17 (ANALYTICS-CORE-1 S3, [analytics-kernel § Distribution Steps](../analytics-kernel.md#distribution-steps)).*

**Function.** Every row gains a **bin number** (0 … bins − 1) and a **label** (`[lower, upper)`) for a number column —
amount bands, age bands, deciles.

**Behaviour.** The SQL is the Analytics Kernel's (`Binning`), a JVM and a DuckDB form held equal by a parity test.
- **`equal_width`** (default) — `bins` bins of equal width over the group's minimum … maximum, or over a stated `min`
  / `max`. Bin `i` is `[lo + i·w, lo + (i+1)·w)`; **the last bin is closed**, so the maximum is in it. A value equal to
  an edge opens the next bin. All values equal: bin 0. **Out of range** (a stated range only): a value below `min` or
  above `max` gets **no bin** (empty number and label) — never clamped into the end bins.
- **`quantile`** (equal frequency) — the edges are the group's quantiles `Q(i / bins)` (`quantile_mode` `continuous`,
  the default, or `discrete`); the bin is the number of interior edges at or below the value, so **ties always share a
  bin** (the higher one when a value equals an edge) and heavy ties can leave a bin empty. Deterministic — not `ntile`,
  which splits ties at random.
- **Per group** with `group_by` (a NULL key is a group of its own). An empty value gets no bin. The label prints the
  edges as DuckDB prints a `DOUBLE` (`[250.0, 500.0)`), `]` for the last bin.
- The column must be a number; `bins` 1–1,000. `min` / `max` serve equal width only, `quantile_mode` quantile only —
  the other method's keys are checked but have no effect. Every row is kept. Runs **at rest**; not admitted mid-branch.
- **Histogram:** no separate Step — `binning` followed by `summarize` (`group_by: [bin, bin_label]`, `measures:
  [count]`) is the histogram, and `ColumnProfiler.histogram` (the profiler's one-column histogram) computes the **same
  equal-width bin** (one shared expression); that profiler form also lists empty bins.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `column` | string | required | — | **Number column.** The number binned. |
| `bins` | number | required | — | **Bins.** How many, 1–1,000, numbered from 0. |
| `method` | select | optional | `equal_width` | **Method.** `equal_width` · `quantile`. |
| `group_by` | list | optional | — | **Groups.** Bin each group over its own range or quantiles. |
| `min` | number | advanced | — | **Range from.** Equal width only; below it, no bin. |
| `max` | number | advanced | — | **Range to.** Equal width only; above it, no bin. |
| `quantile_mode` | select | advanced | `continuous` | **Quantiles.** Quantile only: `continuous` · `discrete`. |
| `bin_column` | string | advanced | `bin` | **Bin column.** Receives the bin number. |
| `label_column` | string | advanced | `bin_label` | **Label column.** Receives `[lower, upper)`. |

Refused at save, at compile and at run with the same words (`DistributionStep.parseBinning`): an unknown key, no
`bins` or one outside 1–1,000, an unknown method or quantile mode, `min` not below `max`, equal output names, a
non-identifier column, and (against the declared schema) a column it lacks, an added column that collides, a text
column.

**Example.** `examples/07-steps/outliers` — after the outlier flags, `bins: 4, min: 0, max: 1000` puts each payment in

## `correlation` → `transform.stats.correlation` — Pearson correlation & linear regression

*Added 2026-10-17 (ANALYTICS-CORE-1 S3, [analytics-kernel § Distribution Steps](../analytics-kernel.md#distribution-steps)).*
Catalog `transform.stats.correlation` is **DELIVERED**: Pearson (default) and Spearman (`method: spearman`, 2026-10-18).

**Function.** How strongly two number columns move together, and the straight line that fits them — per group, for
every pair of the listed columns. **Summarising**: the output is one row per group per pair, not the input rows.

**Behaviour.** DuckDB's `corr`, `regr_slope`, `regr_intercept`, `regr_r2`, `regr_count` (`CorrelationSql`), whose JVM
definitions are `Stats.correlation` / `Stats.linearRegression`.
- **Pairs:** for `columns: [A, B, C]` the pairs are (A, B), (A, C), (B, C), in that order; in each the **later column
  is regressed on the earlier** (`B = intercept + slope · A`).
- **Output columns:** the `group_by` columns (their own names and types), `x_column`, `y_column` (the pair's names),
  `n` (pairs with **both** values present), `correlation` (Pearson's r), `slope`, `intercept`, `r2`. Rows ordered by
  the group values (empty key last), then the pairs as listed.
- **No number is empty, never NaN:** a constant side (one pair included) has no correlation; a constant x has no line;
  a constant y with a varying x has slope 0 and `r2` 1 (a flat line fits it exactly — DuckDB's rule). No complete pair:
  `n` 0 and every figure empty.
- ⚠ DuckDB's streaming covariance loses digits when the values sit on a large common offset (measured: slope off by
  about 5e-12 relative at 1e6, 1.7e-9 at 1e9, 5e-6 at 1e12); subtract a reference first for such data.
- The columns must be numbers; 2–50 columns (up to 1,225 pairs); a group column may not also be correlated nor take an
  output column's name. Runs **at rest**; not admitted mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `columns` | list | required | — | **Number columns.** Every pair is correlated. |
| `group_by` | list | optional | — | **Groups.** One row per group per pair. |
| `method` | select | optional | `pearson` | **Method.** `pearson` (on the values) or `spearman` (on the within-group average ranks; ties share their average rank). Spearman's `slope` / `intercept` / `r2` describe the line through the ranks. |

**Example.** `examples/07-steps/correlation` — 10 orders, `columns: [PRICE, QUANTITY, DISCOUNT]` by `REGION`: 6 rows;
NORTH price → quantity r = −0.9995, slope −2.4265.

## `running` → `transform.running` — Running calculations & moving windows

*Added 2026-10-06 (catalog `transform.analytics.running`; the operator lifted the Step Processor hold and
named this one first (operator, 2026-10-06)).*

**Function.** A rolling calculation per key: `count`, `sum`, `avg`, `min` or `max` of a column over the
rows of the same partition that lie inside a window ending at the current row, ordered by a time column.
Every inbound row is kept and gains one column per measure. Velocity, moving average and rolling total
are this step.

**Behaviour.** It compiles to ONE DuckDB window query:
`SELECT *, fn(col) OVER w AS "as" … FROM input WINDOW w AS (PARTITION BY … ORDER BY "order_by" <frame>)`.

- **Duration window** (`window: 60m`, units `s` · `m` · `h` · `d`): `RANGE BETWEEN INTERVAL n <unit>
  PRECEDING AND CURRENT ROW`. Both ends are **inclusive**, so a row exactly 60 minutes earlier counts.
  `order_by` must be a `TIMESTAMP`, `TIMESTAMP WITH TIME ZONE` or `DATE` column. Any other type is refused.
- **Row window** (`window: 5 rows`, or a bare integer `5`): `ROWS BETWEEN 4 PRECEDING AND CURRENT ROW`,
  meaning the current row and the 4 before it. Rows with equal `order_by` values have no defined order between
  them, so a row window over ties is not deterministic. Use a duration window, or order by a unique column.
- A row whose `order_by` is NULL is framed only with the other NULL rows of its partition.
- `count` with no `column` is `count(*)`. `count(col)` skips NULLs, as do the other four functions.
- **State is per run, never across runs.** The window sees only the rows this one run reads. A key's
  activity in an earlier batch is invisible, so a burst that spans two batches is under-counted. ⚠ For
  velocity across batches, keep using the SQL-over-sink approach: a `sql.template` Job over the landed
  Dataset, as the payment pack's `pf_instrument_velocity` does.

**Safety.** Nothing the author writes is spliced into SQL as text. Every column name (`partition_by`,
`order_by`, `measures[].column`, `measures[].as`) must match `[A-Za-z_][A-Za-z0-9_]*` and is
double-quoted. `fn` is one of five fixed words. The window size is parsed to a positive integer and
re-printed, and the unit maps to a fixed DuckDB keyword. The run refuses a column the inbound data lacks,
and an `as` that collides with an inbound column or a sibling measure. The same checks run at save, in
`ConfigRoutes.stepConfigFindings` (ERROR when active, WARNING on a draft).

**Configuration.** `partition_by`, `order_by` and `window` are form attributes. `measures` is a list of
maps (`{fn, column, as}`), and the shared `list` widget authors only strings. So `measures` has no
attribute spec, exactly like `transform.route`'s `branches`. It is authored in the flat file or the recipe,
and the node form's additional-config editor carries it through a save unchanged.

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `partition_by` | list | optional | — | **Partition by.** The key columns. Each key gets its own window. Leave it blank to treat the whole batch as one key. |
| `order_by` | string | required | — | **Order by (time column).** The column the window slides along. A duration window needs a TIMESTAMP or DATE column. |
| `window` | string | required | — | **Window.** A duration (`60m`, `24h`, `30s`, `7d`) or a row count (`5 rows`). |
| `measures` | list of `{fn, column, as}` | required | — | `fn` ∈ count · sum · avg · min · max. `column` is optional for `count` only. `as` names the output column. |

It runs **at rest**, like every `steps:` kind, so an active pipeline carrying it needs `output_store:`.
It does not arm mid-branch (`RouteArming.BRANCH_STEP_KINDS`).

**Example.** `examples/07-steps/running`: card-payment attempts get a 60-minute attempt count and amount
sum per `INSTRUMENT_TOKEN`, a single-batch version of the payment pack's instrument velocity.

## `hash` → `transform.hash` — Salted one-way hasher

*Added 2026-10-06 (catalog `quality.crypto.hash`, operator 2026-10-06).*

**Design (decided before build).**
- **Namespace.** The node type is `transform.hash` with `steps:` kind `hash`, and the catalog id stays
  `quality.crypto.hash`. `NodeTypeStepKinds.isKnown` only recognises `transform.<kind>`; that is the trap the
  profile Step hit.
- **Flat home.** It is `steps:` only (`FlatHome.STEP`) and has no legacy `processing.*` block. Like `lookup` and
  `sql`, a chain carrying it is never "legacy-shaped".
- **Key.** The key is the Space's own mask key, `EvidenceMasker.forSpace(SpaceConfigRoot.current())`. It is 32
  random bytes in `<config root>.secrets/.risk-score-mask.key`, created on first use. The token is
  `masked:<16 hex>` of an HMAC-SHA-256 (64 bits), the SAME token Link Analysis and audit masking give that
  value. A hashed column therefore joins with itself across runs and with those surfaces. This key was chosen
  over `FailureText`'s `value-fingerprint.salt` because that salt is resolved from a `PipelineConfig`'s dirs,
  which a `RowShaper` node does not hold. It also sits beside config rather than in the Space's secrets
  (operator, 2026-10-06).
- **The key never enters SQL.** DuckDB 1.5 has no HMAC, and inlining the key as a literal would put it in
  query text, profiles and error messages. Instead each column's DISTINCT values are hashed in Java, written to
  a scratch `TEMP` map table, and LEFT JOINed back. The map is DROPPED in a `finally`: left behind, it would be a
  reversal table. ⚠ Memory cost: one Java string per distinct value per column per batch. That is acceptable
  at batch grain and would not be at a whole-history rebuild.
- **Fail closed.** A run with no Space config root is refused, never hashed unkeyed. An unknown column is
  refused, because hashing four of five named columns ships the fifth in the clear. A `salt:` / `key:` key is
  refused at compile and at save. Every refusal names the column and never a value.

**Behaviour.** Each named column is replaced in place by its token (the column becomes VARCHAR), or with
`keep_original: true` the column stays and `<col>_hash` is added beside it. NULL stays NULL. Row counts never
change. The same value gives the same token within a Space and a different token in another Space.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `columns` | list | required | — | **Columns to hash.** Each named column is replaced by a salted one-way token (masked:<16 hex>), the same within this Space so it can still be joined on. |
| `keep_original` | boolean | optional | — | **Keep the original column.** When on, the original column stays and the token is added as <column>_hash. Off (the default) replaces the value in place. |

**Refused at save** (`ConfigRoutes.stepConfigFindings`): no `columns`, any key other than the two above (a
`salt` by name), or a column the declared schema does not carry.

**Example.** `inspecto/examples/07-steps/hash` hashes `ORDER_ID` (8 rows in, 8 rows out).
**Tests.** `RowShaperHashTest` checks determinism, the Space-key equality, cross-Space difference and NULL. Its
leak probes check that no raw value or key bytes appear in any table left behind, and that no value appears in
refusal text. `StepConfigSaveFindingsTest`, `RecipeCompilerTest` and
`NodeConfigNameContractTest.hashAttributesReachTheEngine` cover the save gate, compile and round trip.

## `mask` → `transform.mask` — PII masking (🔒 Enterprise)

*Added 2026-10-06 (catalog `quality.pii.mask`, board SEC-08, operator 2026-10-06).*

**Design (decided before build).**
- **Choosing columns.** Columns are chosen BY CLASSIFICATION, BY NAME, or both (a union).
  - By classification: `classifications: [PII, MSISDN]` with `dataset: <registry id>`. A column's class is the
    Dataset's own `columns[].classification` merged with `EvidenceMasker.lineageClassification`. That covers
    sibling Datasets over the same store and the pipeline schemas behind it, the resolver `publish.postgres` and
    evidence masking already share.
  - Several classes on one column resolve **strictest-wins** (`ColumnClassification.stricter`). The SELECTED set
    is the masked predicate, so a selected class outranks a stricter unselected one. Example: a column that is
    PII on one Dataset and MSISDN on its sibling is masked by a PII-only mask.
  - Untraceable lineage (`UNKNOWN_LINEAGE`) is refused rather than guessed.
- **Modes.**
  - `full` writes `****`.
  - `partial` writes stars plus the last `keep_last` characters (default 4). A value no longer than `keep_last`
    is masked whole.
  - `hash` delegates to `transform.hash`'s Space-keyed token.
  - NULL stays NULL.
  - ⛔ There is **no reversible tokenization vault** (operator 2026-10-06), and a `vault:` key is refused by name.
- **Edition (SEC-08).** `EditionFeatures.PII_MASK` (`quality.pii.mask`) is declared only by `inspecto-policy`
  (`PolicyEditionFeatures`), the module only the Enterprise and Preview flavours bundle. It follows the G9 pattern:
  - The save gate (`pipelineRefusals(draft)`, route-branch steps included) refuses with `ERR_EDITION_FEATURE`.
  - So does the pipeline load (`pipelineRefusals(cfg)`).
  - `RowShaper.mask` itself calls `EditionFeatures.require` before reading a value.
- **One rule list.** `MaskSpec.problems` is shared by `RecipeCompiler` and the save gate, so the shape rules
  cannot drift.
- **Fail loud.** These are refused, each naming columns or classes and never a value:
  - an unknown named column;
  - an unknown Dataset;
  - no Space bound while classifications are set;
  - a mask that resolves to NO inbound column.

**Configuration.**

| `classifications` | list | optional | — | **Mask classifications.** Mask every column the Dataset classifies as one of these (MSISDN, IMSI, ACCOUNT, PII). A column with several classes is judged by its strictest. |
| `dataset` | string | optional | — | **Classified Dataset.** The registry Dataset whose column classifications (and their lineage) choose the columns. Required with classifications. |
| `columns` | list | optional | — | **Mask columns.** Columns masked by name, in addition to any chosen by classification. |

| `keep_last` | number | optional | 4 | **Keep last N characters.** Partial mode only. |

## `route` → `transform.route` — Router

**Function.** Content-based routing into operator-defined branches, each writing its own destination.

**Behaviour.** `mode: case` labels each row by the first matching branch `where:` (first match wins)
and sends the rest to `default:`; `mode: clone` lets a row leave on every matching branch. Row
conservation holds: in = Σ branches. Branches pair with `sinks[]` destinations **by `database`** — the
join key — so every armed branch needs a `key` and a `database` matching exactly one `sinks[]` entry,
exactly one branch is the default, and a duplicated database refuses (rows would land nowhere).
A branch may chain its own `steps[]` (filter · consignment-scope dedup · summarize) before its sink.
Route lives on the **ingest lane** (the branch-aware executor gives each branch key its own sink), so
the at-rest lift refuses a route step; switching a branch's sink off *parks* its rows for a later
*drain* ([step-park-drain](step-park-drain.md)). Multi-schema pipelines cannot arm a route.

**Configuration.** The contract exposes `mode`; keys, predicates and destinations are the branch rows:

```
sinks[2]{database,format}:
  <dir-a>,CSV
  <dir-b>,CSV
route:
  mode: case
  default: <key>
  branches[2]{key,where,database}:
    <key-a>,"<predicate>",<dir-a>
    <key-b>,"<predicate>",<dir-b>
```

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `mode` | select (case · clone) | required | `case` | **Route mode.** Branch keys, predicates and destinations are edited on the branch rows in the Recipe view. |

**Example.** `examples/07-steps/route` (domestic / other, `CENTRAL` caught by the default) ·
`spaces/default/config/route_step`.

## `sink` → `sink.persistent` — the resting store

**Function.** Writes the batch to a resting store: Parquet (snappy / zstd / gzip) or CSV files,
Hive-partitioned `year=/month=/day=` by the schema's `partitionKey` (a non-date key lands in the
default partition), or a DuckLake catalog (`output.ducklake`, PostgreSQL sidecar, Professional+).

**Behaviour.** The store name (`mapping.canonicalName`) is the join key everything downstream reads —
Jobs, enrichments, Datasets. `filename_column` stamps each row with its source file (lineage also
lives in the per-file / batch / lineage ledgers regardless). `priority` is a **share** weight when
execution slots are contended, never precedence; the `intake.*` caps are this pipeline's admission
override of the fleet-wide `-Dingest.maxFilesPerCycle`. A pipeline has one primary sink
(`dirs.database` + `output:`) or several through `sinks[]` — several are constructible and liftable,
but execute only when a `route:` pairs them.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `database` | string | required | — | **Database directory.** Directory where committed batches land. The pipeline's primary sink must set this; a quarantine sink writes unmatched files to 'dir' instead. |
| `format` | select (CSV · PARQUET) | required | `PARQUET` | **Output format.** Stage-1 output file format; absent = Parquet (the engine default). A CSV store is text: it reads back VARCHAR whatever the schema declares. |
| `compression` | string | optional | — | **Compression.** Codec for the output (e.g. snappy / zstd / gzip); blank = format default. |
| `filename_column` | identifier | advanced | — | **Source filename column.** Adds a column of this name carrying each row’s source file. New pipelines default to file_name; blank = no column (lineage stays in the ledger only). |
| `priority` | number | advanced | — | **Priority.** Share weight (1-3) for this pipeline's consignments when execution slots are contended: 3 gets ~3x the throughput share of 1. Shares, never precedence — a priority-1 pipeline always keeps making progress. Blank = 1. |
| `pool` | string | advanced | — | **Execution pool.** Named execution pool this pipeline's consignments are admitted in. Pools are defined server-side (scheduler settings); admission only — a pool never widens the thread or memory caps. A name the server does not define runs in 'default'. Blank = default. |
| `intake.max_files_per_cycle` | number | advanced | — | **Intake cap (files/cycle).** This pipeline's admission cap, overriding the -Dingest.maxFilesPerCycle global (default 500, operator 2026-10-06); 0 = explicitly unbounded (exempts this pipeline from a fleet-wide cap). Blank = inherit the global. |
| `intake.min_files_per_cycle` | number | advanced | — | **Intake cap floor.** Floor the adaptive controller may halve this pipeline's cap down to. Blank = inherit -Dingest.minFilesPerCycle. |
| `intake.adaptive` | boolean | advanced | — | **Adaptive intake control.** Whether cycle overrun adjusts this pipeline's cap; off pins it at the stated cap. Blank = inherit -Dingest.backpressure.adaptive. |
| `ducklake.enabled` | boolean | advanced | — | **Register in DuckLake.** After each committed batch, register the written Parquet files in a DuckLake catalog. Blank = off. Needs catalog URL, data path and table. |
| `ducklake.catalog_url` | string | advanced | — | **Catalog URL.** The DuckLake catalog backend, attached as ducklake:<this>. |
| `ducklake.data_path` | string | advanced | — | **Data path.** The catalog's DATA_PATH. A relative path resolves under the Space directory; an object-store URI is kept as written. |
| `ducklake.schema` | string | advanced | — | **Schema.** Catalog schema the table is created in. Blank = main. |
| `ducklake.table` | string | advanced | — | **Table.** Catalog table the files are inserted into; a batch that lands in a table sub-directory uses that name instead. |

The `ducklake.*` keys (the "DuckLake catalog" group, added 2026-09-23) lower to `output.ducklake:`, or to
the node's own `sinks[]` entry. An entry without its own block inherits `output.ducklake`
(`PipelineConfig.resolveSinks`), and `DuckLakeRegistrar` registers each sink's files in that sink's lake.
`ConfigSafetyValidator` refuses an enabled block that lacks `catalog_url`, `data_path` or `table` (and
path-jails `data_path`). The `ducklake.*` leaves are not declared in `ConfigSpecs.pipeline()`: `output` is
accepted whole. On one node a failed registration is logged and the batch succeeds. With
`-Dinspecto.topology=partitioned`, a failed or missing registration fails the batch. The rules are in
`DuckLakeRegistrar.requireRegistrationConfigured` and `onRegistrationFailure`.

**Example.** `examples/07-steps/sink` (CSV + `SOURCE_FILE`) · `04-output/csv-output` ·
`spaces/default/config/sink_step` · `_reference/ducklake-sink` (`output.ducklake`, needs a PostgreSQL
catalog — shape-correct, not runnable offline).

## `webhook` → `sink.webhook` — the outbound webhook

*Catalog `sink.api.webhook`, DELIVERED 2026-09-23. Professional and Enterprise only.*

**Function.** POSTs the at-rest chain's output rows as JSON to an **https Connection**, `batch_size`
rows per request. Body: `{consignment, sink, batch, batches, rows: [{column: value, …}]}` (`batch` is
1-based). A value goes as a JSON number, boolean or string when it is one, and as its string form
otherwise (dates, timestamps). An empty relation sends nothing.

**Flat home.** The top-level `webhook:` block, carried verbatim as the node's config:

```
output_store: orders_out
webhook:
  connection: orders_hook
  batch_size: 250
  retry: {count: 3, backoff: EXPONENTIAL, initial_delay: 1s, max_delay: 30s}
```

The canvas palette offers it (catalog `addable`). The recipe verb `webhook:` compiles, and `RecipeConverter` projects it back. ✅ Nothing more is owed in the SPA: the Recipe view was deleted (`6d3c68fa`, 2026-09-18), and the lists it read — the served `GET /pipelines/step-types` catalogue, the client `RECIPE_VERBS` fallback and the mock lift/lower in `pipeline-editable.ts` (dead since `f1553136`) — were deleted 2026-09-24 (`STEP-TYPES-DEAD-CLIENT-MIRRORS-1`; `WEBHOOK-RECIPE-PALETTE-1` refuted 2026-09-23). `pipeline-editable.ts` keeps only `isProjectionSlot`.

**Egress (operator decision 2026-09-23).** ⛔ **There is no `url:` and no token key.** The block
names a Connection whose connector is `https`. Onboarding one needs the admin-only
`canOnboardConnections` grant, so a pipeline author can send rows only to an endpoint an administrator
already approved. The engine builds `https://<host>[:<port>]<base_path>`. Plain `http` is not a scheme
it can build. The bearer token is the Connection's `password`: a `SecretResolver` reference, resolved
at send time and never logged. The per-request timeout is the Connection option `timeout_seconds`
(default 10). A Connection that declares a **tunnel or proxy is refused**, because the sink dials
through neither, and quietly bypassing a proxy is worse than refusing. Redirects are never followed:
a 3xx fails the request. The parser refuses an authored `url:`/`token:`/`endpoint:` by name, and refuses
any unknown key rather than defaulting it.

**Lane.** At rest only. `PipelineLift.stageTwo` hangs `sink.webhook` as a **second commit branch**
off the chain's end, beside the `output_store:` sink. It is not downstream of that sink: both consume
the same relation. A webhook with no `steps:` still lifts ("send what landed"). `prepare()` refuses an
**active** pipeline carrying `webhook:` when it has no `output_store:`, a `route:`, or a multi-schema
layout, because on those lanes the webhook would never be reached. `IngestSinkWriter` throws by name
as a backstop.

**Failure semantics: fail the branch, like the persistent sink.** Each POST runs under `retry:`
through the Collector's own `RetryPolicy`. Every attempt carries the same
`Idempotency-Key: <consignment>:<sink>:<batch>` header, and a retry re-sends the identical body. When
a batch runs out of retries, the write throws, `BranchCommitCoordinator` records the branch as failed,
and the source is not finalised. ⚠ Batches the receiver has already accepted stay accepted, because
HTTP has no rollback. A re-run re-sends them under the same keys, so the receiver must de-duplicate
on the key. Keys stay stable across re-runs only as far as the relation's row order does, and the
sink adds no `ORDER BY`.

✅ **No Recipe-view gap** (`WEBHOOK-RECIPE-PALETTE-1`, refuted 2026-09-23): the `webhook:` verb compiles and
the canvas palette adds the node; the Recipe view whose client-side verb lists lacked it was deleted in `6d3c68fa`.

**Edition (EDG-01).** The engine defines the `WebhookSinkTransport` SPI and ships **no**
implementation. The one provider, `HttpWebhookSinkTransport`, lives in `inspecto-notify-channels`
next to `WebhookChannel` and reuses its POST (`WebhookChannel.send`). On Personal there is no
provider, so the write refuses and names the edition. A dry run (`DryRunSinkWriter`) resolves the
whole target the same way, so it refuses exactly what a real run would, then sends nothing. The **graph**
dry run and run-to-here (`PipelineDryRun`) call the same `WebhookSink.plan` for every webhook branch they
reach, so they refuse 422 the same way (G8, 2026-09-23; before, they showed the branch as healthy).
`package.ps1` fails the build if the jar loses the SPI entry.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `connection` | autocomplete | required | — | **Connection.** An https Connection. It carries the endpoint (host, port, path) and the bearer-token reference. |
| `batch_size` | number (1–10000) | optional | `500` | **Rows per request.** Rows sent in one JSON POST. |
| `retry.count` | number | advanced | `0` | **Retries per request.** Extra attempts after a rejection or timeout. Every attempt carries the same Idempotency-Key. |
| `retry.backoff` | select | advanced | `EXPONENTIAL` | **Retry backoff.** EXPONENTIAL · LINEAR · FIXED, full-jittered, capped at `max_delay`. |
| `retry.initial_delay` | duration | advanced | `1s` | **First retry delay.** |
| `retry.max_delay` | duration | advanced | `60s` | **Longest retry delay.** |

**Code.** `WebhookSink` (plan + deliver) · `WebhookSinkTransport` (SPI) · `PartitionSinkWriter` /
`DryRunSinkWriter` (dispatch) · `PipelineConfig.Webhook` · `providers/inspecto-notify-channels/…/HttpWebhookSinkTransport`.
Tests: `WebhookSinkTest`, `WebhookSinkLiftLowerTest`, `PipelineConfigWebhookTest`,
`HttpWebhookSinkTransportTest` (a JDK `HttpServer` stub), `NodeConfigNameContractTest#webhookAttributesReachTheEngine`.

## `excel` → `sink.excel` — the Excel workbook sink

*Catalog `sink.file.excel`, DELIVERED 2026-10-06. Every edition.*

**Design (operator, 2026-10-06).** The operator named `sink.file.excel`: write one or more relations as
named **sheets** of a single `.xlsx`, reusing the report job's workbook path (`ASSURE-XLSX-ATTACHMENTS-1`)
rather than duplicating it. As built:

1. **Node type `sink.excel`, flat home the top-level `excel:` block** — the same shape as `sink.webhook`
   (catalog id `sink.file.*`, node type `sink.<thing>`). A second commit branch beside the `output_store:`
   sink, at-rest lane only; `prepare()` refuses an active pipeline whose chain would never reach it
   (no `output_store:`, a `route:`, a multi-schema layout) and `IngestSinkWriter` throws by name as the backstop.
2. **"One or more relations" = one or more `sheets:`, each a read-only `sql` over the branch's relation
   (alias `input`)** — the `transform.sql` rule, checked by `SqlGuard` at load and at save. A sheet with no
   `sql` is `SELECT * FROM input`.
3. **One writer, extracted.** `ReportXlsx` moved to `com.gamma.pipeline.XlsxWorkbook` (public) and gained
   `writeSheets`: each sheet goes through the same sealed DuckDB connection (`excel` loaded explicitly, rows as
   bound parameters, configuration locked to the output directory) and the same formula neutraliser, then
   `XlsxSheetMerger` stitches the one-sheet parts — DuckDB's writer rewrites a file on every `COPY`. The
   report job calls the same class.
4. **Sheet names are REFUSED, not repaired** — Excel's rule: 1–31 characters, none of `[ ] : * ? / \`, no
   leading or trailing `'`, not `History`, unique ignoring case. (The report job still sanitises its one name.)
5. **Row cap per sheet, fail closed.** `max_rows` (default 100000, ceiling 1048575 = Excel's row limit minus the
   header). A sheet over the cap FAILS the branch; a sink never truncates silently.
6. **Path jail.** `path` is relative to the Space's data root, ends `.xlsx`, carries no `..` segment (refused at
   load), and is re-checked at write time with `PathJail.require` against the data root (symlinks included).
   The workbook is written beside the target and moved into place atomically; each run replaces it.
7. **Fail closed without the extension.** No loadable `excel` binary ⇒ the write throws with every remedy
   named (`ExcelExtension`), the branch fails and the source is not finalised.

**Flat home.**

```
output_store: orders_out
excel:
  path: reports/orders.xlsx
  max_rows: 50000
  sheets:
    - {name: Orders}
    - {name: By region, sql: "SELECT region, count(*) AS orders FROM input GROUP BY region"}
```

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `path` | string | required | — | **Workbook path.** Under the Space's data root, ends `.xlsx`; replaced on every run. |
| `sheets` | list of `{name, sql}` | required | — | **Sheets.** One sheet per entry, in order; `sql` is a read-only SELECT over `input` (blank = every row). |
| `max_rows` | number (1–1048575) | optional | `100000` | **Rows per sheet.** A sheet over the cap fails the branch. |

**Code.** `ExcelSink` (plan + write) · `XlsxWorkbook` (the shared writer) · `XlsxSheetMerger` ·
`PartitionSinkWriter` / `DryRunSinkWriter` (dispatch) · `PipelineConfig.Excel`. Tests: `ExcelSinkTest`,
`ExcelSinkLiftLowerTest`, `PipelineConfigExcelTest`, `XlsxWorkbookTest`,
`NodeConfigNameContractTest#excelAttributesReachTheEngine`. Demo: `inspecto/examples/07-steps/excel-sink`.

⚠ **Known edges.** A sheet whose query returns no rows is written with a single `(no rows)` header — the
shared writer takes its header from the rows, so the column names are lost. `sheets` has no form attribute
(it is a list of maps; the `list` widget is `string[]`): the drawer keeps it as a typed additional-config row.
The write-time symlink check (`ExcelSinkTest#aSymlinkOutOfTheDataRootIsRefusedAtWriteTime`) SKIPS on a
Windows host without symlink rights; the `..`/absolute refusals are pinned everywhere.

✅ **A file above one second of `rate_limit` is throttled, not hung (2026-09-24, `RATE-LIMIT-OVERSIZE-HANGS-1`).**
`RateLimiter.acquire` (inspecto-acquire; its only caller is `RemoteAcquisitionHandler`, once per whole file with
`rf.size()` before the fetch — there is no per-chunk acquire) used to loop until the bucket held `bytes` tokens,
but the bucket is capped at one second of rate (the burst), so an oversized request never completed. Operator
decision — **proportional wait**: a request the bucket cannot cover drains it and sleeps once for
`(bytes − available) / rate`; the refill accrued during that sleep pays the deficit and is discarded, so the
bucket never goes negative (no debt borrowed from later requests) and the long-run rate is honoured. Requests
within the bucket behave as before. Pinned by `RateLimiterTest` (proportional wait, throughput over five
oversize requests = rate, a following small request pays only normal refill; the old loop times out three of
them) and the re-enabled `CollectorProcessorRemoteCycleTest#aFileLargerThanOneSecondOfRateIsThrottledNotHung`.
✅ **A MOVE's archive tree is excluded from discovery (2026-09-23, `POST-ACTION-MOVE-RECOLLECTS-ARCHIVE-1`).**

archived files under `archive/…` and MOVE them again to `archive/archive/…` every cycle.
`CollectorProcessor.excludeArchiveTree` drops them right after `discover`, before stability, gap detection and
fetch; date tokens in the template match any digits, so every past day's `archive/yyyy/MM/dd` tree is excluded,
not just today's. ⚠ The row's "duplicate rows" half was not reproduced: content dedup already refused the
re-ingest — the observable defect was the repeated re-MOVE (and a re-fetch per cycle). Pinned by
`CollectorProcessorRemoteCycleTest#anArchivedFileIsNotCollectedAgain`, plus `#aFileArchivedOnAnEarlierDayIsNotCollectedAgain`
(`archive_path: archive/yyyy/MM/dd` with a file already under `archive/2026/09/01/`; turning off the date-token
matching makes it red, with the old file ingested and today's file collected again) and
`#ftpAnArchivedFileIsNotCollectedAgain` (FTP's MOVE target is `basePath/archive_path/<relativePath>`, the same
under-the-root shape as SFTP, driven against an in-process Apache FtpServer; dropping the exclusion re-MOVEs the
file to `archive/archive/…`).

## Adding a node type — what is declared once, what is derived, what is legitimately separate (2026-09-15)

`NODE-TYPE-MIRRORS-1` measured the cost of adding ONE node type at ten hand sites and asked for the mirrors to
be DERIVED. As-built:

| Site | Now |
|---|---|
| `BuiltinNodeType` case | ✅ source of truth — and it now carries the **flat-config home**: `FlatHome.NONE` / `BLOCK` / `STEP` + the `steps:` kind. A constructor guard refuses a `STEP` without a kind and a kind without `STEP`. |
| `PipelineEditable.LOWERABLE` | 🔁 **derived** — every case whose `flatHome() != NONE` |
| `PipelineEditable.STEP_KIND` | 🔁 **derived** — every `STEP` case's `stepKind()`; `BuiltinNodeTypeFlatHomeTest` pins each kind to a `PipelineConfig.Step` constant, TRANSFORM-only, unique |
| `inspecto-ui/…/node-attributes.ts` | 🔁 **derived** — imports `node-attributes.contract.json` (the JSON `NodeAttributesContractTest` regenerates from the Java table) instead of a hand-typed copy; its spec now pins shape, not equality with itself |
| `NodeAttributes` (spec + `byType` + registration) | ⛔ **stays** — a form schema (widget / tier / default / help / options per key) is a richer structure than an enum field can carry; it IS the attribute-spec table, not a mirror of one |
| `ProcessorCatalog` | ⛔ **stays** — a many-to-many PRODUCT taxonomy that includes PLANNED processors with no node type at all; its own javadoc forbids folding it into the enum |
| `RecipeCompiler` ×2, `RowShaper`, `ConfigSpecs` block | per-node work by nature, out of scope |

⚠ **What the derivation did NOT fix, stated so nobody thinks it did:** `FlatHome.BLOCK` is still a CLAIM that
lift/lower code exists for the type — the `LOWERABLE` trap moved onto the enum case, it did not disappear.
The guard that would catch a false claim is the round trip in `NodeConfigNameContractTest`; add the new type to
it. ⚠ The `transform.<kind>` namespace rule (site 0) is still stated nowhere the compiler can see.
