# Step catalog — every Step kind, delivered and pending

A **Pipeline** is a chain of **Steps**: `collect → parse → transform steps… → sink`. Two vocabularies
describe the chain, and this page is the one place both are laid out side by side:

1. **Step kinds** — the 16 authorable node types the engine executes today
   (`step-types.contract.json`, served as `GET /pipelines/step-types`). Each has a recipe **verb**
   (what the Recipe view and `steps[]` chain call it) and a **node type** (what the graph, the flat
   file and the palette call it). Part A documents every one.
2. **Step Processors** — the 119-entry product taxonomy the palette lists in eight families
   (`processor-catalog.contract.json`, `ProcessorCatalog.java`, served as
   `GET /pipelines/processor-catalog`). A processor is a *label* over a Step kind or an engine
   capability, never a Java class of its own ([catalog-vs-executors](../engine/catalog-vs-executors.md)).
   Part B lists all of them by status: **34 delivered**, **18 partial**
   (something ships, not as a chain Step, or not the whole promise), **67 planned**
   (the palette shows them inactive — *"Not yet available"*). The board rendering of the same list is
   [`EDITIONS.md` § Step Processors](../../../EDITIONS.md); both come from one contract, regenerated by
   `ProcessorCatalogContractTest` with `-Dprocessor.catalog.write=true`, never hand-edited.

## The two lanes (read this before authoring a chain)

| Lane | Steps that execute there | How it runs | Example runner |
|---|---|---|---|
| **Ingest** | `collect`, every `parse` frontend, `route`, `sink` | The poll cycle: files land as Consignments, parse + map + sink in one pass. `route:` forks the write into one destination per branch. | `run-example …` (one shot) |
| **At rest** | `filter`, `dedup`, `join`, `summarize`, `sql` — the `steps[n]:` chain | Stage-1 lands the store; a `type: pipeline` Job (`pipeline_config: <the same file>`, `on_pipeline: <id>`) lifts the chain (`PipelineLift.stageTwo`) and runs it over the landed store on every commit, writing the top-level `output_store:`. A chain with no `output_store:` refuses to lift; an active pipeline whose chain no Job runs is an orphan finding. | `serve-example … --demo` |

Two grammars spell the same chain: the **flat file** (`steps[n]:` list of single-key maps, or the
legacy singular `processing.dedup:` / `processing.join:` / `processing.summarize:` / `csv_settings.where` /
`route:` blocks — mutually exclusive with `steps[]`, projected in the order `filter → join → dedup →
summarize → route`) and the **recipe** (`RecipeCompiler`), which compiles to the flat form. Route
branches may chain their own `steps[]`, limited to `filter` (with `where:`), `dedup` (consignment scope)
and `summarize` — `RouteArming.BRANCH_STEP_KINDS`; a `join` or a nested `route` refuses at save and at
registration. Mechanism detail: [execution-lanes](execution-lanes.md), [live-execution](live-execution.md),
[editable-round-trip](editable-round-trip.md).

**Every delivered Step kind has a runnable example** in two places: standalone under
[`inspecto/examples/`](../../../../inspecto/examples/README.md) (`07-steps/` + `02-parsing/`) and, wired
together in one space, `spaces/default/config/<kind>_step/` (+ `asn1_example`, `xml_example`, and the
format-example pack), seeded by `spaces/default/data/samples/seed-inbox.{sh,ps1}`.

# Part A — the delivered Step kinds

Configuration tables are the served `AttributeSpec`s (key · type · tier · default · help), the same
contract the editor renders. **Flat-file spelling:** a key shown as `a.b` is nested (`a: { b: … }`) in
the `*_pipeline.toon`; a `list` is `key[n]: v1, v2`. Tier is the editor's disclosure bucket
(required · optional · advanced), not validation.

## `collect` → `acquisition` — the Collector

**Function.** The pipeline entry: discovers the files (or the Dataset snapshots) one run will take,
lands them in the inbox, and decides what counts as *new*. Exactly one per pipeline (`collector()` is
singular by construction).

**Behaviour.** Each acquire cycle lists the source through the Connection's connector (`local` inbox,
SFTP/FTPS, JDBC export, Azure Blob, Kafka, or `dataset` to consume another pipeline's parquet
snapshots), applies the include/exclude patterns, the stability window, the file-grain duplicate
policy (`path` marker · `metadata` · `checksum` · `etag`) and the post-success action, then packs the
admitted files into Consignments (`consignment.max_files` / `max_bytes`, ordered by arrival `mtime` or
`name`). Compressed inputs are unpacked here with fail-closed caps. Gap detection over a numbered series
(`gap_detection.sequence: ORDERS_{yyyyMMdd}`) raises `SEQUENCE_GAP`. The trigger keys give the pipeline
its own cadence or make it fire on a Dataset write.

**Flat-file home.** The `collector:` block plus `dirs.poll`, `processing.file_pattern`,
`processing.duplicate_check` / `marker_extension` / `retention_days`, `processing.unpack`, and the
top-level `trigger:`. The UI flattens the nested keys with `__`, shown here as dots.

**Refusals.** `connector: dataset` without `dataset:` (and the reverse) refuse at load. A Connection
that is not `local` needs a saved Connection profile.

**Examples.** `examples/07-steps/collect` · `spaces/default/config/collect_step` (include/exclude,
recursion, gap detection) · `05-acquisition/*` and `06-serve/{sequence-gap,checksum-change,
incremental-watermark}` for the duplicate and gap policies.

## `parse` → the seven `parser.*` frontends

**Function.** Turns a landed file into typed rows named by the schema's `raw.fields[]`
(`selector` = position, header name, JSON key, capture group or dotted record path, depending on the
frontend). The schema also carries the **mapping** — the Record Transformer that shapes those rows —
so `parse` and `map` are one node in the graph. Structural mismatches are rejected to `errors/`
(or the file is quarantined), never silently dropped; type-cast failures become NULL through `TRY_CAST`.

**Configuration.** The `parsing:` block: `frontend:` picks the family, and one sub-block carries that
family's grammar. A `parsing.grammar: grammar/<id>` reference (or a path) reuses a saved Grammar
component; inline keys win. `processing.schema_file` names the schema; `processing.csv_settings.date_formats`
/ `timestamp_formats` are required for any DATE / TIMESTAMP column, whatever the frontend.
The served step-type contract carries no per-frontend attributes: the parse surface is schema-driven
by the served grammar (`parsing-attributes.ts` in the UI). The keys each frontend reads:

| Frontend (node type) | `parsing.` block and its keys | Selector means | Example |
|---|---|---|---|
| `parser.delimited` | `delimited: {delimiter, quote, comment, has_header, skip_header_lines, skip_junk_lines, skip_tail_lines, null_strings[], date_formats[], timestamp_formats[], strict_mode, engine}` | column position (`"0"`) or header name | `01-ingest/hello-csv`, `02-parsing/pipe-delimited`, `02-parsing/no-header`, `csv_example` |
| `parser.fixedwidth` | `fixedwidth: {record: line\|bytes, trim, min_record_length, fields[n]{name,start,length}}` | field name from the slice table | `02-parsing/fixedwidth`, `fixedwidth_example` |
| `parser.json` | `json: {format: auto\|newline\|array, records_path, maximum_object_size}` | JSON key (dotted path) | `02-parsing/json-frontend`, `json_example` |
| `parser.text_regex` | `text_regex: {pattern}` — named capture groups; a non-matching line is dropped | group name | `02-parsing/text-regex-frontend` |
| `parser.xlsx` | `xlsx: {sheet, range, header, normalize_names, ignore_errors, stop_at_empty}` — DuckDB `read_xlsx`, needs the `excel` extension (`ExcelExtension`, cached or `-Dduckdb.extension.dir`), loaded fail-closed | normalised header cell | `02-parsing/xlsx-frontend`, `excel_example` |
| `parser.asn1` | `asn1: {grammar (inline X.680 text), root_type, strictness: BER\|DER\|CER, file_header_length, record_header_length, segments: {recordType: schemaPath}}` — sugar for the plugin wiring below with `Asn1RecordIngester` | dotted path into the decoded record (`party.number`); `EVENT_TYPE` is derived | `02-parsing/asn1-frontend`, `asn1_example` |
| `parser.plugin` | `plugin: {ingester: <FQCN of a StreamingFileIngester>, segments: {recordName: schemaPath}, ingester_config: {…plugin keys}}` (legacy spelling `processing.ingester` / `segments` / `ingester_config`). Shipped ingesters: `XmlRecordIngester` (`record_element`, `namespace_aware`, `encoding`), `FixedWidthRecordIngester` (`record_length`), `Asn1RecordIngester`. | one schema per **segment** (record kind); undeclared kinds are counted as junk | `02-parsing/xml-plugin-frontend`, `xml_example` |

**Refusals.** An unknown `frontend` is refused with the list. `frontend: asn1` beside an explicit
`plugin:` block refuses (two bindings). A plugin ingester with no `segments` refuses. A schema type
outside the engine's DuckDB scalar list refuses at load. A parser is always format-specific: the
generic `parser` type is authoring-legacy, retyped to `parser.<frontend>` on Apply.

**Behaviour worth knowing.** `has_header` skips the header; `skip_header_lines` is *added on top* for
junk preamble. Plugin-ingester pipelines have **no single schema**: the planner labels their
consignments `schema` (a `null` there threw until 2026-09-06). A segment's output lands under
`database/<segmentKey>/`.

## `transform` → `transform.filter` — Row filter

**Function.** Keep or drop rows. Two shapes: a **post-map SQL predicate** (`where:`, over the typed,
mapped columns — the one an explicit `steps[]` filter runs), and the **pre-parse text filters**
(`include_regex` / `exclude_regex` / `include_prefixes` / `exclude_prefixes` against one raw column,
`filter_target_column`) that speak raw-column vocabulary.

**Behaviour.** `RowShaper.filter` splits the input into `data` (kept) and `dropped` — a counted reject
relation, so nothing disappears unaccounted. A NULL predicate result drops the row. Mid-branch (inside
`route:`) a filter must carry `where:`; a blank predicate or a pre-parse key refuses to arm. At rest the
legacy pre-map filter (`csv_settings.where`) is refused because the landed store no longer has raw columns.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `where` | string | required | — | **Row predicate (after parsing).** SQL over the mapped, typed columns. Rows matching are kept; NULL results are dropped. |
| `include_regex` | list | optional | — | **Include matching (before parsing).** Keep rows whose target column matches any of these regexes, checked on the raw text before parsing. |
| `exclude_regex` | list | optional | — | **Exclude matching (before parsing).** Drop rows whose target column matches any of these regexes. |
| `include_prefixes` | list | optional | — | **Include by prefix (before parsing).** Keep rows whose target column starts with any of these. |
| `exclude_prefixes` | list | optional | — | **Exclude by prefix (before parsing).** Drop rows whose target column starts with any of these. |
| `filter_target_column` | number | advanced | — | **Target column index.** Which raw column (0-based) the four before-parsing lists above match against. Ignored by the row predicate. |

**Example.** `examples/07-steps/filter` (8 → 4 rows) · `spaces/default/config/filter_step`.

## `lookup` → `transform.lookup` — Lookup & static map transcoder

**Function.** Transcode one column's values through an inline static map — `NEW → Open`, `SHIPPED → Done`
— without a reference store. The first PARTIAL Step Processor delivered (2026-09-06); a *versioned* lookup
that changes over time is still `transform.join` over a `produces: reference` pipeline.

**Behaviour.** `RowShaper.lookup` compiles the map to a `CASE CAST(column AS VARCHAR) WHEN 'k' THEN 'v' …
END` — keys and values are author **literals**, quoted through `sqlStr`, never SQL and never guarded as SQL.
In place (`SELECT * REPLACE`) unless `target` names a new column; an unmatched value passes through unchanged
unless `default` sets the literal it becomes. Comparison is textual, so a numeric code column maps without a
cast. Emits `data` only — a lookup changes values, never row counts. No legacy singular spelling: a chain
holding one always takes the `steps:` form (like `sql`); the recipe verb is `lookup`, config verbatim.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `column` | string | required | — | **Column to transcode.** The typed, mapped column whose values are looked up. |
| `mappings` | list | required | — | **Mappings (key=value).** One entry per code: the value found, `=`, the value to write. The one spelling — a map-valued attribute type is refused on purpose. |
| `target` | string | optional | in place | **Write to column.** A new column for the result; blank replaces the source column. |
| `default` | string | optional | pass through | **Unmatched values become.** The literal written when no mapping matches. |

**Example.** `examples/07-steps/lookup` (8 rows, `STATUS_LABEL` = Open/Done/Void) · `spaces/default/config/lookup_step`.

## `dedup` → `transform.dedup` — Record deduplicator

**Function.** Record-grain distinct by business key — one row per `keys[]` value. Not file dedup:
that is the Collector's `duplicate:` policy / marker `duplicate_check`, a Guarantee that rides the
Collector.

**Behaviour.** `ROW_NUMBER() OVER (PARTITION BY keys ORDER BY order_by)`: the first row per key is
kept as `data`, the rest form a counted `duplicate` relation. With `scope: window(P4D)` the winners are
also claimed in the durable dedup ledger so a key admitted by an earlier Consignment inside the window
is suppressed too (D-9, at rest only); a window without `order_by` refuses, at save and at run, because
a ledger must never record a non-deterministic winner. Mid-branch only the consignment scope arms.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `keys` | list | required | — | **Dedup keys.** Rows sharing these column values are duplicates; the first (per "Order by") is kept. |
| `order_by` | string | optional | — | **Order by.** Which duplicate wins — SQL ordering over the typed columns; blank = input order. REQUIRED once Scope declares a window: a durable ledger must never record a non-deterministic winner. |
| `scope` | string | advanced | — | **Scope.** How far back a key is a duplicate: blank/consignment = within this Consignment only; window(<ISO-8601 period>), e.g. window(P4D), also suppresses keys admitted by earlier Consignments inside that window via the durable dedup ledger (runs at rest). |

**Example.** `examples/07-steps/dedup` (12 → 9 rows, newest version of each order) ·
`spaces/default/config/dedup_step`.

## `join` → `transform.join` — Reference join

**Function.** Enrich rows from a **Reference Dataset** by key.

**Behaviour.** Always a `LEFT JOIN … USING(on)`: an unmatched key keeps its row with NULL reference
columns, never a silent drop; a non-key column shared by both sides fails loudly rather than writing an
ambiguous result. `reference` is `reference/<pipeline>` (a versioned reference store read through
`ReferenceReader`, current/as-of like the Stage-2 enrichment) or a plain CSV/Parquet path. The
reference is resolved once per run into a scratch view. **At rest only**: the ingest walk carries no
reference resolver, so a mid-branch join refuses with the remedy *run it at rest via output_store:*.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `reference` | autocomplete | required | — | **Reference.** The registered Reference component joined onto the row set. |
| `on` | list | required | — | **Join keys.** Column(s) equated between the rows and the Reference. |

**Example.** `examples/07-steps/join` (8 rows, 6 enriched, WEST deliberately unmatched) ·
`spaces/default/config/join_step` over `spaces/default/data/ref/region_dim.csv`.

## `sql` → `transform.sql` — the Record Transformer

**Function.** One author `SELECT` over the typed input relation, addressed by the fixed alias
`input`; the engine rewrites it to the real relation at execution. This is also the **projection slot**
after every parser (the schema's `mapping.fields[]` compiles to it) and the Record Transformer of the
editor: `transform.record` in the processor catalog, folded 2026-09-04 from expression, cast and
trim processors — one grid, one compiler.

**Behaviour.** A node carrying `fields[]` / `columns` / `rules` is a **projection** and compiles
through `RecordTransform` (the same `[{name, expr}]` seam the browser's grid renders); a hand-written
`sql` string takes the opaque path: `SqlGuard.check` refuses anything but a read-only SELECT (no
DDL/DML, one statement), and saving one yields the `SQL_STEP_UNAUDITED` warning (a WARNING never blocks
a save). Types are derived without a run by `POST /components/transform/describe` (`TypeFlow.describe`,
execution-free DESCRIBE); only a DuckDB binder 422 blocks Apply. In the editor the Step is two peer
views — a **Fields** grid over the function catalog and the **SQL** — with the bounded reconciler
(projections only, catalog templates matched in reverse and re-compiled to prove the round-trip, the
rest kept verbatim as custom rows; a `WHERE`/`JOIN` disables the Fields tab with the reason)
([schema-mapping-authoring](../../frontend/features/schema-mapping-authoring.md) §0).

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `sql` | multiline | required | — | **SQL.** One SELECT statement over the typed input relation, addressed by the fixed alias 'input' (FROM input) — the engine rewrites it to the real relation at execution. No DDL/DML, no multiple statements. |

An authored `fields[]` (`{id, name, from, fn, args}` over `sql-functions.ts`) may ride beside `sql`;
the engine reads only `sql`.

**Example.** `examples/07-steps/sql` (8 → 7 rows, NET and SIZE_BAND derived) ·
`spaces/default/config/sql_step`; the projection form is every `*_schema.toon` `mapping.fields[]`.

## `summarize` → `transform.summarize` — Group-by summarizer

**Function.** A GROUP BY rollup with algebraically composable measures.

**Behaviour.** Measures speak the **one measure grammar** (`measure-grammar.contract.json`) that the
BI query and a materialize Job also use: `count` | `agg(field)` with `agg` ∈ count · countDistinct ·
sum · avg · min · max; result columns are the stable `agg_field` ids (`count`, `sum_gross`,
`max_unit_price`). `group_by` is optional — omit it for one grand-total row. Compiled by
`MeasureCompiler`, so a summarize node, a materialize Job and a dashboard query cannot drift.
Arms mid-branch.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `group_by` | list | required | — | **Group by.** Grouping columns of the rollup. |
| `measures` | list | required | — | **Measures.** Aggregate expressions computed per group. |

**Example.** `examples/07-steps/summarize` (8 rows → 4 REGION groups) ·
`spaces/default/config/summarize_step`.

## `route` → `transform.route` — Router

**Function.** Content-based routing into operator-defined branches, each writing its own destination.

**Behaviour.** `mode: case` labels each row by the first matching branch `where:` (first match wins)
and sends the rest to `default:`; `mode: clone` lets a row leave on every matching branch. Row
conservation holds: in = Σ branches. Branches pair with `sinks[]` destinations **by `database`** — the
join key — so every armed branch needs a `key` and a `database` matching exactly one `sinks[]` entry,
exactly one branch is the default, and a duplicated database refuses (rows would land nowhere).
A branch may chain its own `steps[]` (filter · consignment-scope dedup · summarize) before its sink.
Route lives on the **ingest lane** (the branch-aware executor gives each branch key its own sink), so
the at-rest lift refuses a route step; switching a branch's sink off *parks* its rows for a later
*drain* ([step-park-drain](step-park-drain.md)). Multi-schema pipelines cannot arm a route.

**Configuration.** The contract exposes `mode`; keys, predicates and destinations are the branch rows:

```
sinks[2]{database,format}:
  <dir-a>,CSV
  <dir-b>,CSV
route:
  mode: case
  default: <key>
  branches[2]{key,where,database}:
    <key-a>,"<predicate>",<dir-a>
    <key-b>,"<predicate>",<dir-b>
```

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `mode` | select (case · clone) | required | `case` | **Route mode.** Branch keys, predicates and destinations are edited on the branch rows in the Recipe view. |

**Example.** `examples/07-steps/route` (domestic / other, `CENTRAL` caught by the default) ·
`spaces/default/config/route_step`.

## `sink` → `sink.persistent` — the resting store

**Function.** Writes the batch to a resting store: Parquet (snappy / zstd / gzip) or CSV files,
Hive-partitioned `year=/month=/day=` by the schema's `partitionKey` (a non-date key lands in the
default partition), or a DuckLake catalog (`output.ducklake`, PostgreSQL sidecar, Standard+).

**Behaviour.** The store name (`mapping.canonicalName`) is the join key everything downstream reads —
Jobs, enrichments, Datasets. `filename_column` stamps each row with its source file (lineage also
lives in the per-file / batch / lineage ledgers regardless). `priority` is a **share** weight when
execution slots are contended, never precedence; the `intake.*` caps are this pipeline's admission
override of the fleet-wide `-Dingest.maxFilesPerCycle`. A pipeline has one primary sink
(`dirs.database` + `output:`) or several through `sinks[]` — several are constructible and liftable,
but execute only when a `route:` pairs them.

**Configuration.**

| Key | Type | Tier | Default | What it does |
|---|---|---|---|---|
| `database` | string | required | — | **Database directory.** Directory where committed batches land. The pipeline's primary sink must set this; a quarantine sink writes unmatched files to 'dir' instead. |
| `format` | select (CSV · PARQUET) | required | `CSV` | **Output format.** Stage-1 output file format; absent = CSV (the engine default). |
| `compression` | string | optional | — | **Compression.** Codec for the output (e.g. snappy / zstd / gzip); blank = format default. |
| `filename_column` | identifier | advanced | — | **Source filename column.** Adds a column of this name carrying each row’s source file. New pipelines default to file_name; blank = no column (lineage stays in the ledger only). |
| `priority` | number | advanced | — | **Priority.** Share weight (1-3) for this pipeline's consignments when execution slots are contended: 3 gets ~3x the throughput share of 1. Shares, never precedence — a priority-1 pipeline always keeps making progress. Blank = 1. |
| `intake.max_files_per_cycle` | number | advanced | — | **Intake cap (files/cycle).** This pipeline's admission cap, overriding the -Dingest.maxFilesPerCycle global; 0 = explicitly unbounded (exempts this pipeline from a fleet-wide cap). Blank = inherit the global. |
| `intake.min_files_per_cycle` | number | advanced | — | **Intake cap floor.** Floor the adaptive controller may halve this pipeline's cap down to. Blank = inherit -Dingest.minFilesPerCycle. |
| `intake.adaptive` | boolean | advanced | — | **Adaptive intake control.** Whether cycle overrun adjusts this pipeline's cap; off pins it at the stated cap. Blank = inherit -Dingest.backpressure.adaptive. |

**Example.** `examples/07-steps/sink` (CSV + `SOURCE_FILE`) · `04-output/csv-output` ·
`spaces/default/config/sink_step`.

# Part B — the Step Processor catalog (the palette's taxonomy)

The palette lists **119** processors in eight families. A **delivered** processor is a label over a
Step kind or an engine capability that ships today; the *Maps to* column says which. A **partial**
processor has something real behind it, but not as a chain Step or not the whole promise — the
*What exists today* column is the honest boundary. A **planned** processor renders inactive in the
palette (*"Not yet available"*): no engine code, no config keys; adding one is a product decision
(a new Step kind needs a `BuiltinNodeType`, a `RowShaper` arm or a contributed `PipelineNodeExecutor`,
a `PipelineEditable` LOWERABLE + STEP_KIND + lift registration, and the runtime steps→graph seam — the
four registrations [catalog-vs-executors](../engine/catalog-vs-executors.md) names). The board's
edition cells and the two Enterprise-only rows live in `tools/render-processor-board.mjs`.

## Keeping this page true

- **Part A's tables are the served contracts.** When `NodeAttributes` or a parse grammar changes,
  regenerate `step-types.contract.json` (`mvn -o test -Dstep.types.write=true`) and rebuild the tables
  from it; do not retype a help string here.
- **Part B is the processor contract, verbatim.** Change `ProcessorCatalog.java`, regenerate with
  `-Dprocessor.catalog.write=true`, then re-render this part and `EDITIONS.md`
  (`node tools/render-processor-board.mjs`). A processor moves from *planned* to *delivered* only when
  a Step kind executes it; *partial* is the honest middle and should name what is missing.
- **Every delivered Step kind keeps its example runnable** — `inspecto/examples/07-steps` and
  `spaces/default/config/<kind>_step`. Run `bash inspecto/examples/run-example.sh 01-ingest/hello-csv`
  after touching the path jail or the launchers: the examples sit outside every test.
