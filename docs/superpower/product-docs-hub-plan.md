## 1. Problem

Documents are organised by **audience tier** and by **when they were written**, not by what is sold and
built. One module's truth sits in up to six places, and nothing ties them together:

| What | Where today |
|---|---|
| Requirement of record (plan) | `docs/okf/capabilities/<area>/` (capability ≠ module) |
| Mechanism / implementation | `docs/okf/backend/**`, `docs/okf/frontend/features/**` |
| L3 module page (architecture, screens, API) | `docs/stakeholders/modules/` (its own slugs, e.g. `collectors` for module `acquire`) |
| User / admin guidance | sections of `USER_GUIDE.md`, `ADVANCED_GUIDE.md`, `docs/ops/` |
| API | `docs/api/openapi-v1.json` (one file, not sliced per module) |
| Feature list | `FEATURE_INVENTORY.md`, `EDITIONS.md` |

The commercial tree in `product-map/` (layer → module → add-on → solution pack → edition) already
models the onion and is kept honest by `tools/check-product-map.mjs`. Its `docs:` field points at one
page per item (20 of ~85 items set). That is the spine the docs should hang off.

## 2. Decision — one hub per Product Map Item

`docs/okf/product/<kind>/<name>/index.md` — the path mirrors `product-map/<kind>/<name>.toon`, so the docs
tree tallies with the assembled Offering by construction. The product-map item's `docs:` points at its hub.

Every hub carries the **same ten document slots** in a table, in this order (a reader and an agent learn
the shape once):

| Slot | Reader | Notes |
|---|---|---|
| `plan` | product owner, developer | requirement of record + what is open |
| `spec` | developer | implementation detail |
| `architecture` | solution architect, advanced user, troubleshooter | design, flows, troubleshooting |
| `features` | marketing, presales | customer-facing feature description |
| `feature-db` | build / release engineer | sortable feature rows — **generated, never prose** (wave 3) |
| `user-guide` | end user | screens and configuration |
| `admin-guide` | system administrator, team manager | install, permissions, operations |
| `api` | API integrator | the module's slice of `/api/v1` — `api-routes.md` is **generated** by `tools/render-api-routes.mjs` (route → registering Maven module, joined with `openapi-v1.json`, drift listed); hand-written `api-*.md` pages sit beside it |
| `tests` | QA / QC | test cases and where their tests live |
| `brochure` | customer, sales | **`n/a` on modules** — brochures are per edition / solution pack |

Slot status: `current` (a file of that slot is in the hub) · `missing` · `n/a`. A file's slot is its
name: `<slot>.md` or `<slot>-<topic>.md`. The hub `index.md` is **generated** by `tools/render-product-docs.mjs`
(CI runs it with `--check`); `tools/docs-relocate.mjs <map.csv> [--write]` moves docs and rewrites every link and
path mention to them (used for wave 4; reuse it for any later move).

### Decisions

- **D-PDH1 ~~Hub first, move later~~ → moved in one pass (operator 2026-10-19: "get rid of all those
  weirdly named documents").** Classification was by title/description; misfiled docs are fixed by a `git mv`
  plus `render-product-docs` — cheap. Cross-cutting backend → `layer.platform`; UI-wide + whole-product
  brochures → `layer.product`.
- **D-PDH2 Facts are not copied.** Editions, roles, dependencies and order codes are read from
  `product-map/` and `offerings/`; a hub names the item id and never restates them.
- **D-PDH3 Cross-cutting concepts stay in OKF sections** (`backend/`, `capabilities/`, …); hubs link them.
  A hub is for one sellable/buildable item.
- **D-PDH4 Hubs inside OKF** (`docs/okf/product/`), and the ONLY current-knowledge tree besides root canon,
  `docs/api/` (the contract) and `compliance/`.
- **D-PDH5 Coverage is enforced, not hoped for.** `tools/check-product-docs.mjs` fails a hub that lacks a
  slot row or uses an unknown status, and reports per-slot coverage; `check-doc-links.mjs` resolves the links.

## 3. Waves

1. ✅ **Pilot** — `module.acquire`, `addon.incidents`, checker, product-map `docs:` links.
2. ✅ **Hubs for every item** — generated by `render-product-docs.mjs`.
3. ✅ **`feature-db`** — `tools/render-feature-db.mjs` (test `render-feature-db.test.mjs`; CI runs `--check` in the
   Product Map guard step) writes `feature-db.md` into every module and add-on hub with rows (28 hubs, 378 rows on
   2026-10-19) and the whole product to `target/product-docs/feature-db.csv`. Columns: feature, type, module,
   editions, addon, status, key, source. **Derived only**: every `provides:` list of a module manifest except
   `contracts`; the processor catalog contract (a processor goes to the module its `requires` names, else its
   `capability`, else `engine`, which owns `ProcessorCatalog`); `FEATURE_INVENTORY.md` §1 rows whose Doc cell links a
   module hub. Editions/add-ons come from `offerings/*.toon`; status from the Product Map Item (the catalog's own
   status or an inventory `[LIVE]`-style tag wins). Edition, layer and solution-pack hubs get no feature-db — their
   rows would be the union of everything; read the CSV. A generated `feature-db.md` the tool no longer writes is
   deleted on the next run. Gotcha: most FEATURE_INVENTORY rows cite no hub, so they are not in the feature-db.
4. ✅ **Move content in** (whole files). Still open: split big multi-audience docs (L3 pages hold screens/API
   sections → `user-guide` / `api`), ✅ `api` route slices generated per module (`render-api-routes.mjs`, CI-checked), fill
   `features` for every item.
   ✅ **`tests` slot generated** (2026-10-19) — `tools/render-tests-inventory.mjs` (test
   `render-tests-inventory.test.mjs`; CI runs `--check` in the Product Map guard step) writes `tests-inventory.md` into
   every `module.*` hub whose Maven module has tests (45 hubs, 1561 classes on 2026-10-19), plus
   `layer/platform/tests-tools-inventory.md` for `tools/*.test.mjs`. Module dir = the dir holding the manifest whose
   `id` matches the item's `module:`; tests = git-tracked `src/test/**/*Test.java` / `*IT.java`. Kind is inferred
   (`*IT` → IT; `ControlApi*` or `HttpClient`+`ControlApi` → real-HTTP control-plane; else unit); summary = first
   Javadoc line. UI specs are deliberately not mapped (no reliable item link). Orphaned generated files are deleted.
5. **Brochures** — per edition and solution pack, assembled from `features` slots.
6. ✅ **Agent skills** (2026-10-19) — four repo skills read hubs by item id + slot:
   `.claude/skills/docs-lookup` (item id + slot → hub `index.md` → slot file), `pipeline-author`
   (etl/engine/config/acquire hubs, SaveGate rules, validate → dry-run routes, tests),
   `incident-investigate` (incidents/ops/event/observability/engine hubs + platform troubleshooting,
   routes, symptom → hub table), `case-analysis` (case-management, la-core, scoring, screening,
   entity-list). Every route is in `docs/api/openapi-v1.json` or the cited hub doc. Still open: skills
   for alert authoring and agentic operation once those hubs have `features` / `api` slots.
